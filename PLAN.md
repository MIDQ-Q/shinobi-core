# 2. Важные архитектурные следствия

## 2.1. Клиентская авторитетность чакры

Так как ты выбрал клиентскую авторитетность, схема будет такой:

- Клиент владеет текущим значением чакры.
- Клиент сам тратит чакру на:
  - чакра-режим;
  - воду;
  - стену;
  - паркурные действия;
  - двойной прыжок;
  - заряженный прыжок;
  - увороты;
  - кувырок;
  - медитацию и т.д.
- Клиент сам считает реген.
- Клиент сам переключает чакра-режим.
- Сервер получает изменения только когда:
  - изменилось текущее значение чакры выше порога;
  - изменился режим;
  - изменилось истощение;
  - изменилась усталость выше порога;
  - игрок зашел в мир;
  - применили админ-команду;
  - произошла смерть/смена измерения/сброс.

Сервер при этом:

- хранит зеркало в компоненте;
- сохраняет данные в мире;
- логирует подозрительные значения;
- не наказывает игрока;
- может передавать данные админ-командам;
- может позже стать валидирующим без переписывания всей архитектуры.

Важно: сервер не должен параллельно сам тратил чакру, иначе будет двойной расход.

---

## 2.2. Передвижение: клиентская физика + серверное зеркало

Для движения:

- Клиент отвечает за ощущение:
  - вода;
  - стена;
  - слайд;
  - кувырок;
  - увороты;
  - двойной прыжок;
  - заряженный прыжок;
  - захват края;
  - ползание;
  - медитация.
- Сервер получает события:
  - вошел в воду;
  - вышел из воды;
  - вошел на стену;
  - вышел со стены;
  - начал слайд;
  - начал ползание;
  - начал медитацию;
  - сделал уворот;
  - сделал кувырок;
  - сделал двойной прыжок;
  - начал заряженный прыжок;
  - отпустил заряженный прыжок;
  - взял край и т.д.
- Сервер только:
  - логирует;
  - хранит состояние для будущего мультиплеерного визуала;
  - мягко повторяет часть физики, чтобы уменьшить резиновую ленту;
  - не откатывает игрока жестко.

# 4. Общий принцип реализации скриптами

Так как базой является текущий дамп от 25 числа, лучше делать не один огромный скрипт, а серию идемпотентных скриптов.

Требования к каждому скрипту:

1. `$ErrorActionPreference = "Stop"`.
2. Кодировка: UTF-8 без BOM.
3. Нормализация переводов строк:
   ```text
   заменить `r`n на `n`
   ```
4. Перед патчем проверять, не применен ли патч уже.
5. Если обязательный паттерн не найден — остановка и ошибка.
6. После каждого скрипта:
   ```text
   .\gradlew.bat build
   ```
7. Все создаваемые участки кода помечать маркерами:
   ```text
   // SHINOBICORE:MOVEMENT_V3:BEGIN
   // SHINOBICORE:MOVEMENT_V3:END
   ```
8. Для новых файлов использовать маркер версии:
   ```text
   // SHINOBICORE MOVEMENT V3 FILE
   ```

## Скрипт 04: серверное зеркало чакры и сохранение

Название:

```text
04_server_chakra_mirror.ps1
```

Цель: сервер должен хранить клиентские значения и сохранять их.

Создать/исправить:

```text
src/main/java/com/example/shinobicore/chakra/server/ServerChakraMirror.java
```

Использовать существующий компонент:

```text
IChakraComponent
```

Если он уже есть в дампе, не заменяем его полностью, а добавляем методы:

```text
updateFromClient()
sanitizeValues()
logSuspicious()
save()
load()
```

Сервер должен:

1. Принимать пакет от клиента.
2. Читать буфер до `server.execute`.
3. Проверять:
   - нет NaN;
   - нет бесконечности;
   - текущая чакра не меньше 0;
   - текущая чакра не выше расчетного максимума слишком сильно;
   - усталость в разумных пределах.
4. Если значения подозрительные:
   - логировать;
   - санитарно обрезать;
   - не кикать.
5. Записать значения в компонент.
6. Пометить компонент как требующий сохранения.

Важно:

- сервер не должен сам тикать реген, если клиент авторитетен;
- сервер не должен сам списывать чакру за движение;
- сервер только зеркало и сохранение.

DoD:

- после перезахода чакра восстанавливается;
- сервер видит актуальные значения;
- нет двойного регена;
- нет двойной траты.

# 7. Детальная клиентская логика чакры

## 7.1. Тик клиента

Псевдокод:

```text
ClientChakraController.tickClient():

если игрок отсутствует:
    сбросить локальное состояние
    выйти

если игрок мертв:
    выключить режим
    выключить медитацию
    выйти

если игрок в меню:
    не обрабатывать клавиши движения
    но продолжать тик состояния

обновить эффективную максимальную чакру

если медитация активна:
    реген = базовый реген * медитационный множитель
    спад усталости = базовый спад * медитационный множитель
    если игрок двинулся или получил урон:
        остановить медитацию

иначе:
    если чакра-режим активен:
        считать стоимость за тик:
            базовая стоимость режима
            + стоимость воды
            + стоимость стены
            + стоимость активных паркурных эффектов

        если чакры хватает:
            потратить чакру
            установить задержку регена
        иначе:
            выключить режим
            установить истощение, если нужно

    иначе:
        если задержка регена истекла:
            восстанавливать чакру

        постепенно снижать усталость

    текущая = 0

    если включено истощение:

    если усталость ниже порога выхода:
        снять истощение

ограничить значения

если состояние изменилось:
    отправить пакет серверу

обновить старые совместимые поля HUD и ClientNinjaState
```

# 8. Детальная логика движения

## 8.1. Приоритеты состояний

Порядок проверки:

```text
1. Игрок мертв/в меню/в транспорте/летит → сброс активных опасных состояний
2. Медитация → блокирует большинство активных действий
3. Стена → если активна, вода не активна
4. Вода → если активна, стена может начаться только при прыжке и выходе из воды
5. Слайд/кувырок/уворот → временные состояния, блокируют медитацию и ползание
6. Ползание → постоянный режим позы, пока не отключен
7. Обычное состояние
```

---

## 8.2. Вода

Вход:

```text
если чакра-режим активен:
    если под игроком вода:
        если игрок около поверхности:
            если не крадется/не ползет:
                если хватает чакры:
                    начать воду
```

Тик:

```text
если вода активна:

    если вода исчезла:
        выйти

    если игрок полностью погрузился:
        выйти

    если чакра закончилась:
        выйти резко

    стабилизировать Y
    не давать накапливать урон от падения
    разрешить горизонтальное движение
```

Выход:

```text
игрок нажал прыжок
игрок начал красться
игрок начал ползти
чакра закончилась
вода исчезла
сервер попросил сброс, если включен админ-сброс
```

---

## 8.3. Стена

Вход:

```text
если чакра-режим активен:
    если было недавнее нажатие прыжка:
        если игрок в воздухе:
            если игрок движется в сторону стены:
                если стена найдена:
                    если блок разрешен:
                        если кулдаун истек:
                            начать стену
```

Тик:

```text
если стена активна:

    обновить нормаль
    если стена исчезла:
        выйти

    если чакра закончилась:
        выйти

    если игрок нажал Space:
        выполнить wall jump
        выйти

    если игрок крадется:
        выйти

    если время на стене превысило лимит:
        выйти

    спроецировать ввод на плоскость стены
    ограничить скорость
    применить уменьшенную гравитацию
    применить мягкое прилипание
    сбросить fallDistance
```

Выход:

```text
wall jump
потеря стены
потеря чакры
приземление
красться
превышение времени
серверный сброс, если включен
```


```text
если игрок в воздухе:
    если движется к блоку:
```

Тик:


# 12. Логирование и подозрительные события

Так как ты выбрал только логирование, сервер не должен наказывать игрока.

Но нужно защитить сервер от мусора.

## 12.1. Санитарная обработка

Сервер всегда обрезает:

```text
NaN
Infinity
отрицательную текущую чакру
слишком огромную текущую чакру
слишком огромную усталость
```

Это не наказание, а защита данных.

---

## 12.2. Подозрительные события

Логировать, если:

```text
чакра изменилась слишком быстро
усталость изменилась невозможно быстро
игрок сообщает, что на воде, но воды рядом нет
игрок сообщает, что на стене, но блока рядом нет
скорость игрока сильно выше допустимой
старт стены без недавнего прыжка, если это запрещено
повторяющиеся пакеты с одним и тем же состоянием слишком часто
```

Формат логов:

```text
[CHAKRA-SUS]
[MOVEMENT-SUS]
[WALL-SUS]
[WATER-SUS]
```

Важно:

- логи должны быть ограничены по частоте;
- нельзя спамить каждый тик;
- в продакшене по умолчанию только подозрительные события, не полный дебаг.

# 13. Совместимость с текущим дампом

## 13.1. Не переписывать все сразу

Так как в дампе уже есть много реализованного, стратегия такая:

1. Оставить совместимые старые поля:
   - `ClientNinjaState.chakraMode`
   - `ChakraHudRenderer.currentChakra`
   - `ChakraHudRenderer.maxChakra`
   - `ChakraHudRenderer.exhausted`

2. Новый контроллер пишет в них значения.

3. Старые системы, которые читают эти поля, продолжают работать.

4. Постепенно переводим старые проверки на новый контроллер.

---

## 13.2. Если уже есть `ParkourManager`

Используем его как основу.

Новые действия должны либо:

- регистрироваться в `ParkourManager`;
- либо вызываться из `ClientMovementService`, если `ParkourManager` уже перегружен.

Главное — не создать две параллельные системы паркура.

---

## 13.3. Если уже есть `ChakraPhysicsClient`

Не удаляем сразу.

Нужно:

1. Оставить его как точку входа, если на него завязаны события.
2. Внутри заменить прямую физику на вызов новых сервисов:
   - вода;
   - стена;
   - двойной прыжок;
   - инерция;
   - совместимые флаги.
3. Убрать дублирующую логику.

---

## 13.4. Если уже есть `NinjaComponents.getChakra`

# 14. Что именно считается “старым кодом”

В твоем вопросе 19 важно уточнение.

Под “старым кодом” в этом плане понимается **не весь дамп от 25 числа**, а только:

1. Остатки сломанной стены из подхода v2:
   - миксин, отменяющий `tickMovement`;
   - серверная компенсация гравитации;
   - принудительный `setPosition`;
   - camera roll;
   - wall model/render crash-миксины.

2. Дублирующиеся обработчики:
   - если одновременно работают старый и новый водный бег;
   - если одновременно работают старый и новый wall run;
   - если есть несколько обработчиков клавиши L.

3. Отладочные выводы:
   - `System.out.println`;
   - debug-блоки, оставшиеся в коде.

Весь остальной текущий код является базой, поверх которой ставим новую реализацию.

# 15. Тестовый контур

## 15.1. Чакра

Проверить:

1. Игрок заходит в мир.
2. Чакра имеет дефолтное значение.
3. `/shinobicore chakra info` показывает данные.
4. `/shinobicore chakra set 50` работает.
5. `/shinobicore chakra add 25` работает.
6. L включает режим.
7. Чакра тратится.
8. При нуле режим выключается.
9. После перезахода значение сохраняется.
10. После смерти режим не остается включенным.
11. Усталость растет от действий.
12. Истощение блокирует режим.
13. Медитация восстанавливает чакру быстрее.

---

## 15.2. Вода

Проверить:

1. Обычная вода.
2. Вода в котле? Котлы можно игнорировать, если не поддерживаются.
3. Waterlogged-плиты/ступени/люки, если есть.
4. Пузырьри.
5. Водоросли.
6. При нуле чакры игрок падает.
7. При прыжке вода отключается.
8. При красться можно разрешить погружение.
9. Нет бесконечного бега по воде без чакры.
10. Сервер логирует, если воды нет.

---

## 15.3. Стена

Проверить:

1. При прыжке в стену игрок прилипает.
2. При простом беге рядом со стеной не прилипает.
3. После выхода кулдаун 1 секунда.
4. После wall jump кулдаун 1 секунда.
5. Отскок мягкий.
6. Отскок в направлении взгляда.
7. Если смотреть в стену, не должно бесконечно вдавливать.
8. Твердые блоки работают.
9. Заборы работают.
10. Стены работают.
11. Стекло работает.
12. Листва работает.
13. Воздух не работает.
14. Без чакры стена отключается.
15. Камера не крутится.
16. Другие игроки не получают позу.

---

## 15.4. Паркур

Проверить:

1. Слайд на земле.
2. Слайд в чакра-режиме длиннее.
3. Двойной Shift ложит.
4. Двойной Shift поднимает.
5. Старый бинд ползания работает.
6. Кувырок дает короткий рывок.

```powershell
function Write-File($path, $content) {
    $dir = Split-Path $path -Parent
    if (-not (Test-Path $dir)) { New-Item -ItemType Directory -Path $dir -Force | Out-Null }
    [System.IO.File]::WriteAllText($path, $content, $utf8)
```

```powershell
function Patch-File($p, $old, $new) {
    if (-not (Test-Path $p)) { Write-Host "  [MISS] $p" -ForegroundColor Red; return $false }
    $c = [System.IO.File]::ReadAllText($p, $utf8)
    $c = $c.Replace("`r`n", "`n")
    $oldN = $old.Replace("`r`n", "`n")
    $newN = $new.Replace("`r`n", "`n")
    if ($c.Contains($newN)) { Write-Host "  [SKIP] already applied: $(Split-Path $p -Leaf)" -ForegroundColor Yellow; return $true }
    if (-not $c.Contains($oldN)) { Write-Host "  [FAIL] pattern not found: $(Split-Path $p -Leaf)" -ForegroundColor Red; return $false }
    $c = $c.Replace($oldN, $newN)
    [System.IO.File]::WriteAllText($p, $c, $utf8)
    Write-Host "  [PATCH] $(Split-Path $p -Leaf)" -ForegroundColor Green
    return $true
}

package com.example.shinobicore.world.spawn;

import com.example.shinobicore.util.ShinobiLogger;
import com.example.shinobicore.world.config.WorldgenConfig;
import net.fabricmc.fabric.api.event.lifecycle.v1.ServerTickEvents;
import net.fabricmc.fabric.api.networking.v1.ServerPlayConnectionEvents;
import net.minecraft.entity.EntityType;
import net.minecraft.entity.mob.MobEntity;
import net.minecraft.registry.tag.BiomeKeys;
import net.minecraft.server.MinecraftServer;
import net.minecraft.server.network.ServerPlayerEntity;
import net.minecraft.server.world.ServerWorld;
import net.minecraft.util.math.BlockPos;
import net.minecraft.util.math.Vec3d;
import net.minecraft.world.World;
import java.util.HashMap;
import java.util.Map;
import java.util.Random;
import java.util.UUID;

public final class EnemySpawnManager {
    private static final Map<UUID, Integer> nightSpawnCount = new HashMap<>();
    private static final Random RANDOM = new Random();
    private static boolean registered = false;

    private EnemySpawnManager() {}

    public static void register() {
        if (registered) return;
        registered = true;
        ServerTickEvents.END_SERVER_TICK.register(EnemySpawnManager::tick);
        ServerPlayConnectionEvents.DISCONNECT.register((handler, client) -> {
            if (handler.player != null) {
                cleanup(handler.player.getUuid());
            }
        });
        ShinobiLogger.info("EnemySpawnManager registered");
    }

    public static void cleanup(UUID playerId) {
        nightSpawnCount.remove(playerId);
    }

    private static void tick(MinecraftServer server) {
        if (server == null) return;
        ServerWorld overworld = server.getOverworld();
        if (overworld == null) return;

        boolean isNight = overworld.isNight();

        if (!isNight) {
            if (!nightSpawnCount.isEmpty()) {
                nightSpawnCount.clear();
            }
            return;
        }

        WorldgenConfig cfg = WorldgenConfig.getInstance();

        for (ServerPlayerEntity player : server.getPlayerManager().getPlayerList()) {
            if (player.getWorld() != overworld) continue;

            UUID id = player.getUuid();
            int count = nightSpawnCount.getOrDefault(id, 0);
            if (count >= cfg.maxNightSpawns) continue;

            // Check biome tag
            var biomeEntry = overworld.getBiome(player.getBlockPos());
            if (!biomeEntry.isIn(net.minecraft.registry.tag.BiomeKeys.IS_FOREST) &&
                !biomeEntry.isIn(net.minecraft.registry.tag.BiomeKeys.IS_JUNGLE)) {
                continue;
            }

            // 1/1200 chance per tick (~1 per minute)
            if (RANDOM.nextInt(1200) != 0) continue;

            // Find spawn position
            double angle = RANDOM.nextDouble() * Math.PI * 2;
            double dist = cfg.minNightSpawnRadius +
                RANDOM.nextDouble() * (cfg.nightSpawnRadius - cfg.minNightSpawnRadius);
            double sx = player.getX() + Math.cos(angle) * dist;
            double sz = player.getZ() + Math.sin(angle) * dist;

            BlockPos spawnPos = new BlockPos(
                (int) sx,
                overworld.getTopY(),
                (int) sz
            );
            spawnPos = overworld.getTopPosition(spawnPos, net.minecraft.world.Heightmap.Type.WORLD_SURFACE);

            // Validate: not in solid block
            if (!overworld.isAir(spawnPos) || !overworld.isAir(spawnPos.up())) continue;

            // Spawn zombie as placeholder enemy
            MobEntity mob = EntityType.ZOMBIE.create(overworld);
            if (mob != null) {
                mob.setPosition(spawnPos.getX() + 0.5, spawnPos.getY(), spawnPos.getZ() + 0.5);
                overworld.spawnEntity(mob);
                nightSpawnCount.put(id, count + 1);
                ShinobiLogger.debug("Night spawn #%d for %s at %s",
                    count + 1, player.getName().getString(), spawnPos.toShortString());
            }
        }
    }
}
```

### 1.1. Расширение статов

Добавить метод `getCategory()`, возвращающий категорию.

### 1.2. Формула опыта и уровней

Используем существующую формулу из `StatsComponentImpl.getXpForNextLevel`:

```
xp_required = XP_BASE + level * XP_PER_LEVEL + level * level * XP_SQUARED
```

где `XP_BASE = 100`, `XP_PER_LEVEL = 25`, `XP_SQUARED = 5`.

**Кривая сложности:**
- Уровни 0–20: требуют ~100–500 XP (лёгкое начало)
- Уровни 20–50: требуют ~500–3000 XP (умеренно)
- Уровни 50–100: требуют ~3000–50000+ XP (хардкор/гринд)

**Настройка через конфиг:**
Добавить в `ShinobiCoreConfig`:
```java
public int xpBase = 100;
public int xpPerLevel = 25;
public int xpSquared = 5;
public int spPerLevelUp = 1;
public int maxStatLevel = 100;
```

### 1.3. Очки навыков (SP)

- При повышении уровня стата игрок получает `spPerLevelUp` очков навыков.
- СП хранятся в `IStatsComponent.getSkillPoints()`.
- СП тратятся в древе навыков на разблокировку узлов.
- СП не зависят от стата — это общий пул.

### 1.4. Источники XP

| Источник | Статы | Множитель | Реализация |
|---|---|---|---|
| Использование техник | Соответствующий стат техники + `CONTROL` | 1.0x | Хук в `JutsuCaster.cast()` после успешного каста |
| Бой с мобами/игроками | `TAIJUTSU`, `KENJUTSU`, `SHURIKEN`, `GENJUTSU` в зависимости от типа атаки | 1.0x | Хук в `LivingEntity.damage()` или `PlayerEntity.attack()` |
| Клановые задания | Несколько статов + репутация | 1.5x | Новая система заданий (в будущем спринте) |
| Свитки | Один конкретный стат | Большой одноразовый | Новый предмет `ScrollItem`, при использовании вызывает `addXp` |
| Тренировочные столбы | Зависит от мини-игры | 2.0x | Интерактивный блок, открывает мини-игру |
| Мини-игры | Соответствующий стат | 2.0–3.0x | Награда в `MiniGameScreen.onSuccess()` |

### 1.5. Сохранение прогресса после смерти

В `NinjaComponentInitializer` уже используется `RespawnCopyStrategy.ALWAYS_COPY` для всех компонентов. Это означает, что прогресс сохраняется после смерти. Ничего менять не нужно.

### 1.6. Роль клана

По твоему выбору: **всё + репутация открывает скрытые техники**.

- Клан даёт стартовые бонусы к статам (уже есть в JSON кланов).
- Клан открывает эксклюзивные ветки древа (поле `clanRequired` в узлах).
- Клан влияет на стоимость/скорость прокачки определённых статов (множители в `costMultiplier` клана).
- Репутация с кланами открывает скрытые техники: если `reputation >= threshold`, узел становится видимым.

**Изменения:**
В `IClanComponent` добавить метод `getReputation(String clanId)`.
В узлах древа добавить поле `reputationRequired`.

```java
        renderBackground(context);
        
        MatrixStack matrices = context.getMatrices();
        matrices.push();
        matrices.translate(width / 2.0f, height / 2.0f, 0);
        matrices.scale(zoom, zoom, 1);
        matrices.translate(-cameraX, -cameraY, 0);
        
        renderBranches(context);
        renderNodes(context, mouseX, mouseY);
        renderConnections(context);
        
        matrices.pop();
        
        renderTooltip(context, mouseX, mouseY);
    }
    
    @Override
    public boolean mouseDragged(double mouseX, double mouseY, int button, double deltaX, double deltaY) {
        if (button == 0) {
            cameraX -= deltaX / zoom;
            cameraY -= deltaY / zoom;
            return true;
        }
        return super.mouseDragged(mouseX, mouseY, button, deltaX, deltaY);
    }
    
    @Override
    public boolean mouseScrolled(double mouseX, double mouseY, double amount) {
        zoom += amount * 0.1f;
        zoom = MathHelper.clamp(zoom, 0.5f, 2.0f);
        return true;
    }
}
```

### 5.5. Разблокировка узлов

**Логика:**
1. Игрок кликает на узел

# 6. Компонент боевого состояния

## 6.1. Зачем отдельный компонент

Нужен новый компонент:

```text
shinobicore:combat_v3
```

Старый `CombatComponent` не используем.

Причина:
- старый боевой код игнорируется;
- новая система должна быть модульной;
- проще тестировать;

# 8. Better Combat интеграция

## 8.1. Антикоррупционный адаптер

Создаём:

```text
compat/BetterCombatAdapter.java
```

Он обязан:

- проверять наличие BC;
- получать категорию оружия из предмета;
- получать текущее комбо, если BC API это даёт;
- слушать события атаки;
- не позволять остальному коду напрямую зависеть от классов BC.

Интерфейс:

```text
boolean isReady()
boolean isMeleeWeapon(ItemStack stack)
WeaponClass resolveWeaponClass(ItemStack stack)
Optional<ComboSnapshot> getComboSnapshot(ServerPlayerEntity player)
void registerAttackListener(CombatAttackListener listener)
void logStatus()
```

---

## 8.2. `CombatAttackListener`

```text
void onMeleeAttackConfirmed(
    ServerPlayerEntity attacker,
    Entity target,
    ItemStack weapon,
    BetterCombatAttackInfo info
)
```

Где `BetterCombatAttackInfo` содержит:

```text
int comboIndex
float damageMultiplier
float attackRange
float angle
Identifier weaponCategory
boolean isCrit
long timestamp
```

Если BC не даёт готовый `comboIndex`, `ComboTracker` считает шаг сам по времени и последовательности атак.

---

## 8.3. Что делает `MeleeCombatService` после события BC

Порядок:

```text
1. Получить игрока.
2. Проверить, что боевой модуль включён.
3. Проверить, что игрок не в action lock.
4. Проверить, что игрок не блокирует.
5. Определить weaponClass.
6. Получить стойку.
7. Обновить комбо.
8. Рассчитать бонусный урон.
9. Применить бонусный урон как магический.
10. Отправить клиентский фидбек.
11. Запустить VFX-событие.
```

# 9. Комбо-система

## 9.1. Общая концепция

Better Combat управляет анимацией и хитбоксом.  
ShinobiCore управляет:

- окном комбо;
- шагом комбо;
- бонусами за шаг;
- сбросом комбо;
- финишером через удар ногой.

---

## 9.2. `ComboTracker`

Поля:

```text
lastAttackTime
currentStep
weaponClass
comboExpireAt
queuedKickFinisher
```

Методы:

```text
void onAttackConfirmed(ServerPlayerEntity player, WeaponClass weaponClass, long now)
int getCurrentStep()
boolean isComboValid(long now)
void reset()
void queueKickFinisher()
boolean consumeQueuedKickFinisher()
float getComboStepBonus(WeaponClassDefinition definition, int step)
```

---

## 9.3. Логика шагов

Для катаны:

```text
Шаг 1: обычный удар
Шаг 2: быстрый удар
Шаг 3: сильный финишер
```

Бонусы:

```text
Шаг 1: +0%
Шаг 2: +5%
Шаг 3: +15%
```

Если игрок нажал удар ногой в нужное окно:
- шаг 3 может быть заменён на финишер-удар ногой;
- урон считается как финишер;
- комбо сбрасывается после финишера.

---

## 9.4. Окно комбо

По умолчанию:
- катана: 1500 мс;
- кунай: 1200 мс;
- безоружный бой: 1000 мс.

Стойки могут менять окно:

```text
aggressive: comboWindowMultiplier = 0.9
defensive: comboWindowMultiplier = 1.0
```

Прогрессия может добавлять бонус:

```text
comboWindowMs * (1 + progressionBonus)
```

# 10. Формула урона

## 10.1. Главный принцип

Не отменять ванильный урон.  
Добавлять сверху магический/шин-урон.

---

## 10.2. Контекст ближней атаки

`MeleeDamageContext`:

```text
ServerPlayerEntity attacker
Entity target
ItemStack weapon
WeaponClassDefinition weaponDefinition
StanceDefinition stance
int comboStep
float comboStackBonus
boolean chakraModeActive
boolean inCounterWindow
long timestamp
```

---

## 10.3. Формула

Базовая формула:

```text
extraDamage =
  weaponDefinition.baseBonusDamage
  * (1 + statLevel * weaponDefinition.statScaling)
  * stance.damageMultiplier
  * clanMultiplier
  * masteryMultiplier
  * chakraModeMultiplier
  * comboStepMultiplier
  * counterWindowMultiplier
  * fatiguePenalty
```

Где:

```text
statLevel = PlayerStatsGateway.getStatLevel(primaryStat)
clanMultiplier = ClanGateway.getMeleeDamageMultiplier(...)
masteryMultiplier = ProgressionGateway.getMasteryMultiplier(...)
chakraModeMultiplier = 1.2 если чакра-режим активен
comboStepMultiplier = 1 + comboStepBonus + comboStackBonus
counterWindowMultiplier = 1.35 если цель только что успешно парировала
fatiguePenalty = от 1.0 до (1 - fatiguePenaltyMax)
```

---

## 10.4. Методы формулы

```text
float calculateMeleeBonus(MeleeDamageContext context)
float calculateThrownBonus(ThrownDamageContext context)
float calculateImbuePayloadDamage(ImbueDamageContext context)
float getBlockReduction(ServerPlayerEntity player, StanceDefinition stance)
float getParryPower(ServerPlayerEntity player, StanceDefinition stance)
```

# 11. Блок

## 11.1. Требования

- удержание клавиши;
- стоимость 3 стамины в секунду;
- снижение урона;
- ломается при нехватке стамины;
- в защитной стойке защищает на 360°.

---

## 11.2. Клавиша

По умолчанию:

```text
Block: Right Shift, hold
```

Но должно быть настраиваемо.

```text
boolean canBlockSource(ServerPlayerEntity player, DamageSource source)
boolean isSourceInProtectionAngle(ServerPlayerEntity player, DamageSource source)
```

---

## 11.4. Логика старта блока

```text
1. Игрок зажимает клавишу.
2. Клиент отправляет пакет:
   combat:set_block_state(true)
3. Сервер проверяет:
   - включён ли блок;
   - не находится ли игрок в action lock;
   - не парит ли игрок;
   - есть ли стамина;
   - не атакует ли игрок в данный момент.
4. Если всё ок:
   component.setBlocking(true)
   синхронизировать клиенту.
5. Если нет:
   отправить отказ.
```

---

## 11.5. Логика серверного тика блока

Каждый тик:

```text
if player.blocking:
    drain = 3.0 / 20.0
    drain *= clanStaminaCostMultiplier
    drain *= progressionBlockCostReduction

    if resources.hasStamina(player, drain):
        resources.drainStamina(player, drain)
    else:
        breakBlock(player, NO_STAMINA)
```

Так как стоимость может быть дробной, используем аккумулятор:

```text
component.addBlockStaminaAccumulator(drain)
if accumulator >= 1.0:
    spend whole part
```

Либо хранить дробную стамину в гейтвее, если система ресурсов это поддерживает.

---

## 11.6. Логика снижения урона

Порядок:

```text
1. Если парирование активно — блок не используется.
2. Если источник не блокируется — урон проходит.
3. Если стойка defensive:
   угол защиты = 360
4. Если стойка aggressive:
   угол защиты = 180
5. Если источник в пределах угла:
   reduction = baseDamageReduction * stance.block.damageReductionMultiplier
   damage = damage * (1 - reduction)
```

Пример:

```text
База: 60%
Aggressive: 60% * 0.8 = 48%
Defensive: 60% * 1.25 = 75%
```

---

## 11.7. Разлом блока

Если стамина закончилась:

```text
component.setBlocking(false)
component.applyActionLock(now, blockBreakActionLockMs)
component.applyBlockBreakCooldown(now, blockBreakCooldownMs)
send feedback BLOCK_BREAK
play sound
spawn particles
```

## 12.5. Кулдаун

По умолчанию:


Если сделать кулдаун от момента нажатия, окно 400 мс почти всегда будет перекрывать кулдаун, и парирование станет слишком сильным.

## 12.6. Успешное парирование ближней атаки

Если в активное окно по игроку прилетает ближняя атака:

```text
1. Проверить, что защитник имеет активное парирование.
2. Проверить угол:
   - defensive: 360°
   - aggressive: 150°
3. Если успешно:
   - урон отменяется;
   - атакующий получает короткий стан/люфт;
   - защитник получает окно контратаки;
   - защитник может получить немного чакры/стамины;
   - проигрывается VFX/SFX;
   - клиент получает событие успеха.
```

Псевдокод:

```text
if defender.isParryActive(now):
    if angleValid(defender, attacker, stance.parry.angle):
        cancelDamage()
        attackerComponent.applyActionLock(now, successStaggerMs)
        defenderComponent.applyCounterWindow(now, counterWindowMs)
        resources.addChakra(defender, parrySuccessChakraGain * clanMult)
        resources.addStamina(defender, parrySuccessStaminaGain)
        feedback(PARRY_SUCCESS)
```

## 18.8. Выполнение техники при попадании

`ImbuedProjectileExecutor`:

```text

    ServerWorld world,
    ServerPlayerEntity caster,
    Entity target,
    ImbuePayload payload,
    ThrownWeaponEntity projectile
)
```

Логика:

```text
1. Найти определение техники.
2. Проверить, что техника всё ещё разрешена.
3. Рассчитать урон:
   jutsu.baseDamage * payloadPowerMultiplier * scaling
4. Применить элемент.
5. Применить статусы:
   - огонь: поджог;
   - молния: замедление/шок;
   - ветер: отброс;
   - вода: замедление;
   - земля: краткое замедление;
   - дым: слепота;
   - яд: отравление.
6. Если техника AoE:
   сделать малый радиус.
7. Если техника снарядная:
   применить как прямой урон.
8. Если техника запрещена для сюрикенов:
```

Не разрешать:
- стены;
- призывы;
- клонов;
- сложные гравитационные техники;
- техники, требующие долгого каста;
- техники с кастом выше 1 секунды, если не разрешено отдельно.

Разрешать:
- маленькие снаряды;
- статусные техники;
- маленькие AoE;
- элементные усиления;
- дымовые/световые эффекты.

## 20.3. Важное правило чтения пакетов

Всегда:

```text
1. Сначала читаем все поля из буфера.
2. Только потом вызываем серверную логику.
```

То есть:

```text
receive(player, buf):
    read all fields
    server.execute:
        validate and apply
```

Это защищает от гонок и падений.

# 26. Современный боевой цикл

После реализации боевой цикл должен выглядеть так:

```text
1. Игрок выбирает стойку.
2. Сближается с целью.
3. Атакует комбо из 3 шагов.
4. Может завершить комбо ударом ногой.
5. Может заблокировать урон, тратя стамину.

9. Может бросить сюрикен или кунай.
10. Может заранее наделить снаряд техникой.
11. Получает обратную связь через анимации, звук, частицы и тряску.
12. Прокачка и клановые бонусы усиливают стиль.
```

# 28. Риски и как их гасим

## 28.1. Риск: Better Combat API нестабилен или недокументирован
Решение:
- весь BC-код только в `BetterCombatAdapter`;
- при нехватке событий делаем точечный миксин в адаптере;
- остальная логика не знает о внутренних классах BC.

---

## 28.2. Риск: безоружный бой плохо поддерживается BC
Решение:
- внутри адаптера разрешён простой серверный удар;
- анимация через PlayerAnimator;
- формулы и урон остаются общими.

---

## 28.3. Риск: парирование 400 мс слишком сильное
Решение:
- кулдаун начинается после окна;
- стамина на попытку;
- короткий люфт при промахе;
- всё настраивается в JSON.

---

## 28.4. Риск: наделённые сюрикены ломают баланс техник
Решение:
- белый список техник;
- множитель силы 0.6–0.7;
- запрет сложных поведений;
- отдельный кулдаун наделения.

---

## 28.5. Риск: клиентский предикшн создаёт иллюзию урона
Решение:
- клиент предсказывает только визуал;
- фактический урон приходит с сервера;
- при расхождении клиент корректируется.

# 1. Зафиксированные проектные решения

## 1.1. Основа
- Делаем **поверх текущей версии 3.0**, не тащим старый код как активную основу.
- Старые системы считаются выключенными, пока явно не включены.
- Никакие модули пока не считаются рабочими, поэтому сначала стабилизация.

## 1.2. Зависимости
Все указанные зависимости **обязательны**:
- Fabric API
- Cardinal Components API
- Better Combat
- GeckoLib
- Cloth Config
- PlayerAnimator

Из-за этого:
- в `fabric.mod.json` можно ставить `depends`;
- но всё равно делаем адаптеры и проверки версий, чтобы падение было понятным.

## 1.3. Режим игры
- Одиночная игра / локальный мир.
- Всё равно сохраняем серверную авторитарность, чтобы не плодить читерские привычки и не ломать логику.

## 1.4. Бой
- Темп: **тактический, но быстрый**.
- Одна кнопка каста для выбранного слота.
- Анимация печатей: простое складывание рук, без сложной хореографии.
- Кулдауны короткие, касты короткие, но есть прерывания, стоимость и телеграфы.

## 1.5. Чакра
- Умеренная стоимость техник.
- Быстрая регенерация чакры.
- При 0 чакры:
  - естественная регенерация блокируется на 10 секунд;
  - медитация может восстанавливать чакру сразу;
  - после 10 секунд обычная регенерация возвращается.

## 1.6. Стихии
- Стартовая стихия назначается случайно.
- Клан может дать дополнительную стихию.
- Стартовые стихии открываются через миниигру аттюнмента.
- Дополнительные стихии — через квестовые линейки.
- Стихийные взаимодействия пока **аркадные**, без глубокой симуляции.

## 1.7. Мир
- Изменение мира разрешено.
- Но делаем это через безопасный менеджер временных блоков, чтобы техники не ломали мир навсегда.

## 1.8. Кланы
- Игрок сам выбирает клан.
- Изученные техники при смене клана **не теряются**.
- Новые клановые техники открываются только если они доступны текущему клану и являются врождёнными/изучаемыми.
- Смена клана разрешена только на нукенинов.

## 1.9. Гендзюцу
- Жёсткие контроля допустимы.
- Длительность контроля зависит от прокачки гендзюцу.
- Мобы получают упрощённые эффекты.
- Игроки получают отдельные эффекты и визуал.
- Боссы имеют сильно повышенный резист.

## 1.10. Сенсорика
- Это не один режим, а **отдельные техники** в древе прокачки.
- Каждая следующая сенсорная техника сильнее предыдущей.

## 1.11. Изучение и прокачка техник
- Новые техники изучаются через:
  - древо навыков;
  - свитки.
- У техник есть уровни, например 1–10.
- Уровень растёт от использования и выполнения условий.

## 1.12. Визуал
- Ванильные частицы и звук.
- Процедурные кубы / воксельные модели.
- Полноценные модели и анимации через GeckoLib / PlayerAnimator.
- Для MVP делаем практичный гибрид: простое должно работать сразу, сложное подключается без переписывания.

## 1.13. Объём
- Делаем **MVP**, но с полноценной архитектурой под дальнейшее расширение.

# 10. Уровни техник 1–10

Это ключевое требование: **техники прокачиваются через использование и условия**.

## 10.1. Модель уровня
У каждой техники:
- `level` от 1 до `maxLevel`
- `uses`
- требования для роста уровня
- изменения параметров по уровням

---

## 10.2. Что повышает уровень
Формула проверки:

```text
canLevelUp =
  uses >= requiredUsesForNextLevel
  && выполнены все условия уровня
  && level < maxLevel
```

## 10.3. Условия уровня
Поддерживаем:
- `stat_level`
- `element_level`
- `element_unlocked`
- `quest_flag`
- `uses`
- `clan`
- `dojutsu_stage`

---

## 10.4. Как меняются параметры
Для MVP используем интерполяцию между базовым и максимальным значением.

Формула:

```text
t = (level - 1) / (maxLevel - 1)

value = baseValue + (maxValue - baseValue) * t
```

Применяем к:
- стоимости
- урону
- дальности
- радиусу
- длительности
- скорости снаряда
- отбрасыванию

---

## 10.5. Пример
Для огненного шара:

```text
Уровень 1:
  стоимость 35
  урон 8
  дальность 24

Уровень 10:
  стоимость 20
  урон 16
  дальность 48
```

На уровне 5 будет промежуточное значение.

---

## 10.6. Эффекты по уровням
Некоторые техники получают новые эффекты на уровнях.

Пример:
```text
уровень 3: добавить слабое горение
уровень 6: увеличить отбрасывание
уровень 10: добавить второй снаряд или больший радиус
```

В JSON:
```json
"levelEffects": {
  "3": ["burn"],
  "6": ["knockback_up"],
  "10": ["extra_projectile"]
}
```

# 12. Каст: одна кнопка и выбранный слот

## 12.1. Клиентский ввод
- Есть одна кнопка каста.
- Она кастует **выбранный слот**.
- Выбор слота делается через меню или команду, но сам каст — одна кнопка.

## 12.2. Рекомендуемые бинды
```text
Cast selected jutsu: R
Open Shinobi menu: K
Select slot 1..9: через меню или временно команды
```

Для MVP можно оставить:
- `/shinobicore jutsu select <slot>`
- выбор слота в меню позже

---

## 12.3. Пакет каста
Клиент отправляет:

```text
C2S_CAST_SELECTED
{
  clientSelectedSlot
}
```

Сервер:
- сверяет выбранный слот с серверным;
- достаёт технику;
- проверяет всё по цепочке.

---

## 12.4. Полный серверный поток

```text
1. Проверить FeatureFlags.enableJutsuCasting
2. Проверить, жив ли игрок
3. Проверить, не находится ли игрок под запретом каста
   - гендзюцу-паралич
   - другой активный каст
   - особый дебафф
4. Получить выбранный слот
5. Получить jutsuId из слота
6. Получить JutsuDefinition
7. Проверить:
   - изучена ли техника
   - доступен ли клан
   - открыта ли стихия
   - пройдены ли статы
   - нужен ли свиток/додзюцу/квест
8. Проверить кулдаун техники и глобальный кулдаун
9. Рассчитать стоимость с учётом уровня, клана, статов и усталости
10. Проверить чакру
11. Определить цель
12. Если каст мгновенный:
    - выполнить сразу
13. Если каст имеет длительность:
    - создать CastSession
    - проиграть анимацию
    - прерывать при уроне/гендзюцу/запрете
14. После успеха:
    - списать чакру
    - добавить усталость
    - поставить кулдаун
    - увеличить uses
    - проверить левелап
    - выполнить behavior
    - отправить визуал и звук
```

---

## 12.5. CastSession
Хранит:

```text
player
jutsuId
levelSnapshot
startTick
endTick
reservedChakra
targetSnapshot
interruptable
movementAllowed
```

Каждый тик проверяет:
- жив ли игрок;
- не начался ли другой каст;
- не прервали ли каст;
- хватает ли чакры;
- не изменился ли цель/таргетинг критично.

---

## 12.6. Очередь каста
Для высокого темпа добавить:

```text
castQueue = одна запись
```

Если игрок нажал каст в последние 0.2 секунды текущего каста:
- сохранить следующий слот;
- после завершения текущего каста попробовать запустить следующий, если хватает чакры и кулдаун позволяет.

Это даёт быстрый темп без спама.

# 13. Формулы баланса

## 13.1. Максимум чакры

```text
maxChakra =
  baseChakra
  + reserveLevel * reservePerLevel
  + clanReserveBonus
  + progressionBonus
```

Ограничение:
```text
maxChakra = min(maxChakra, clanChakraCap)
```

---

## 13.2. Регенерация чакры

```text
baseRegenPerSecond = 4.0
controlRegen = control * 0.15
clanRegen = clanBonus

regenPerSecond = baseRegenPerSecond + controlRegen + clanRegen

if meditating:
  regenPerSecond *= 2.5

if exhausted and not meditating:
  regenPerSecond = 0
```

---

## 13.3. Стоимость техники

```text
scaledCost = JutsuScaler.scaleCost(def, level)

finalCost =
  scaledCost
  * clanCostMultiplier
  * elementCostMultiplier
  * fatigueCostMultiplier
  * controlCostMultiplier
```

Где:

```text
controlCostMultiplier = clamp(1.0 - control * 0.002, 0.75, 1.0)
fatigueCostMultiplier = 1.0 + max(0, fatigue - 60) * 0.004
```

---

## 13.4. Урон техники

```text
scaledDamage = JutsuScaler.scaleDamage(def, level)

finalDamage =
  scaledDamage
  * (1 + ninjutsu * 0.015)
  * (1 + elementLevel * 0.010)
  * clanDamageMultiplier
  * elementalInteractionMultiplier
  * randomVariance
```

`randomVariance` = `0.95..1.05`.

---

## 13.5. Кулдаун

```text
finalCooldown =
  scaledCooldown
  * clanCooldownMultiplier
  * controlCooldownMultiplier
```

Где:

```text
controlCooldownMultiplier = clamp(1.0 - control * 0.001, 0.85, 1.0)
```

И обязательно:
```text
finalCooldown = max(finalCooldown, minGlobalCooldown)
```

---

## 13.6. Длительность гендзюцу

### Потенциал кастера
```text
potency =
  def.potencyBase
  + genjutsuStat * 0.35
  + perceptionStat * 0.15
  + levelBonus
```

### Защита цели
```text
defense =
  target.genjutsu * 0.5
  + target.perception * 0.5
  + clanResistBonus
  + dojutsuResistBonus
  + bossResistBonus
```

### Множитель длительности
```text
durationMult =
  clamp(1 - defense / (defense + potency + 20), 0.15, 1.0)
```

### Максимальная длительность для игроков
```text
maxPlayerDuration =
  clamp(
    def.baseDurationSeconds + caster.genjutsu * def.durationPerGenjutsuStat,
    1.0,
    def.maxPlayerDurationSeconds
  )
```

### Итог
```text
finalDuration =
  min(def.baseDurationSeconds * durationMult, maxPlayerDuration)
```

Для мобов:
```text
finalDuration = def.baseDurationSeconds * mobDurationMultiplier
```

Для боссов:
```text
finalDuration *= def.bossResistMultiplier
```

---

## 13.7. Сенсорика

```text
sensoryRange =
  def.baseRange
  + level * def.rangePerLevel
  + perception * def.rangePerPerception
```

Стоимость в секунду:

```text
chakraPerSecond =
  def.costPerSecond
  * clamp(1.0 - control * 0.002, 0.75, 1.0)
```

## 14.1. Интерфейс поведения

```text
  onTick(session)
  onInterrupt(context)
  getClientFx(context)
```

## 14.2. ProjectileBehavior

### Логика
```text
1. Создать JutsuProjectileEntity
2. Задать:
   - владельца
   - стихию
   - урон
   - уровень техники
   - параметры движения
3. Каждый тик:
   - двигать снаряд вручную
   - применять гравитацию
   - делать рейкаст от предыдущей позиции к новой
   - проверять сущности
   - проверять блоки
4. При попадании:
   - нанести урон
   - применить элемент
   - применить эффекты уровня
   - показать частицы
   - проиграть звук
```

### Важно
- не использовать ванильный снаряд как основу;
- ручной рейкаст;
- хранить `hitEntities`, чтобы не бить одну цель несколько раз.

## 14.3. BeamBehavior

### Логика
```text
1. Создать активную лучевую сессию
2. Каждый тик или раз в 2 тика:
   - брать направление взгляда
   - делать рейкаст
   - искать сущностей в узкой зоне
   - наносить периодический урон
3. Поддерживать:
   - стоимость за тик
   - максимальную длительность
   - прерывание
```

---

## 14.4. AoeBehavior

### Логика
```text
1. Определить центр:
   - точка прицела
   - цель
   - вокруг кастера
2. Найти сущностей в радиусе
3. Применить:
   - урон
   - отбрасывание
   - дебаффы
   - стихийные состояния
4. Показать визуал зоны
```

---

## 14.5. DashBehavior

### Логика
```text
1. Получить направление
2. Применить импульс
3. Во время рывка:
   - проверять столкновения
   - наносить контактный урон, если указан
   - применять эффекты
4. Остановить рывок:
   - по дистанции
   - по таймауту
   - по столкновению
```

Для тактического темпа:
- короткие рывки;
- маленькие кулдауны;
- можно совмещать с атаками, но не делать бесконечные цепочки.

## 14.6. BuffBehavior

### Логика

```text
4. При окончании удалить эффект
```

## 14.7. WallBehavior

Так как ты разрешил изменение мира, делаем стены через **временные блоки**.

### Логика
```text
1. Рассчитать форму стены:
   - ширина
   - высота
   - направление
2. Для каждой позиции:
   - если можно заменить блок
   - запомнить оригинальный блок
   - поставить временный блок
3. Зарегистрировать блок в TemporaryBlockManager
4. По таймеру:
   - удалить временный блок
   - вернуть оригинальный блок, если он не изменён другим источником
```

### Правила
- лимит временных блоков на игрока;
- глобальный лимит;
- не ставить в неразрушимые/защищённые места;
- если блок уже изменён после установки — не возвращать опасное состояние.

# 15. Стихийная система для MVP

## 15.1. Цель
Сделать **аркадную**, понятную и лёгкую систему, без глубокой симуляции.

---

## 15.2. Базовые стихии
```text
fire
water
wind
earth
lightning
none
```

---

## 15.3. Состояния
Для MVP достаточно:
```text
BURNING
WET
CHARGED
MUDDY
```

---

## 15.4. Простые взаимодействия

| Комбинация | Результат | Эффект |
|---|---|---|
| Огонь + Вода | Пар | краткая слепота |
| Молния + Вода | Электрошок | урон + замедление |
| Ветер + Огонь | Усиление | +15% урона |
| Земля + Вода | Грязь | замедление |

---

## 15.5. Как это применять
Функция:

```text
applyElement(target, element, power, source)
```

Алгоритм:

```text
1. Проверить текущие состояния цели
2. Найти взаимодействие
3. Если взаимодействие есть:
   - применить эффект
   - частично снять старые состояния
4. Если нет:
   - наложить новое состояние
```

---

## 15.6. Окружение
Пока не делаем глубокую проверку мира.

Разрешаем только простые вещи:
- если техникой подожгли блок — ставим временный огонь;
- если техника водная и попала в цель — накладываем `WET`;
- если техника земляная и попала в воду/мокрого — может создать грязь.

Без массового сканирования блоков каждый тик.

# 16. Аттюнмент и стихии

## 16.1. Модель стихий игрока

### Поля
```text
innateElements: List<ElementType>
unlockedElements: List<ElementType>
```

---

## 16.2. Стартовое назначение
При первом входе / выборе клана:

```text
1. Выдать 1 случайную стартовую стихию
2. Если у клана есть дополнительная стихия:
   добавить её в innateElements
```

### Пример
- игрок получил случайно `wind`
- клан Учиха даёт дополнительно `fire`
- итоговый `innateElements = [wind, fire]`

---

## 16.3. Открытие через миниигру
- Миниигра открывается из меню.
- Игрок проходит аттюнмент.
- Сервер проверяет:
  - есть ли свободная стартовая стихия;
  - хватает ли SP;
  - хватает ли `control`;
  - не открыта ли стихия уже.
- После успеха стихия переходит из `innateElements` в `unlockedElements`.

---

## 16.4. Стоимость аттюнмента
Формула:

```text
attunementSpCost = 3 + unlockedCount * 2
attunementControlRequirement = 10 + unlockedCount * 5
```

---

## 16.5. Дополнительные стихии через квесты
Для стихий вне стартового набора:

```text
ElementQuestDefinition:
  element
  requirements
  rewardUnlock
```

Требования могут быть:
- уровень стата;
- уровень другой стихии;
- использовать N техник определённой стихии;
- получить предмет;
- завершить квестовый флаг.

Для MVP:
- квесты можно завершать командой или простым автоматическим условием;
- UI квестов делаем позже.

# 17. Гендзюцу

## 17.1. Принципы
- Гендзюцу — полноценная боевая система, а не просто дебафф.
- Игроки получают отдельный визуал и механику снятия.
- Мобы получают упрощённый серверный эффект.
- Боссы имеют высокий резист.

---

## 17.2. Типы гендзюцу для MVP

### `fear`
**Мобы:**
- убегают или теряют цель.

**Игроки:**
- замедление;
- визуальный оверлей;
- лёгкая паника (без принудительного управления).

### `paralysis`
**Мобы:**
- сильное замедление / остановка.

**Игроки:**
- запрет движения;
- запрет каста;
- видимый индикатор снятия.

---

## 17.3. Серверная модель

### `GenjutsuInstance`
```text
id
sourceId
targetId
type
potency
remainingTicks
originalDurationTicks
breakProgress
```

---

## 17.4. Применение
Алгоритм:

```text
1. Проверить цель
2. Проверить иммунитет
3. Рассчитать защиту цели
4. Рассчитать длительность
5. Применить инстанс
6. Если цель игрок:
   отправить клиентский визуал
7. Если цель моб:
   наложить упрощённые эффекты
8. Если цель босс:
   сильно уменьшить длительность
```

---

## 17.5. Снятие гендзюцу

### Способы
1. Урон по цели
2. Активное снятие чакрой
3. Помощь союзника
4. Иммунитет / додзюцу

### Урон
```text
remainingSeconds -= damage * damageBreakFactor
```

### Активное снятие
- отдельная кнопка или действие;
- требует чакру;
- имеет короткий каст;
- прерывается уроном.

Формула стоимости:

```text
breakCost = baseBreakCost + potency * 0.4
```

---

## 17.6. Анти-абьюз
- один активный жёсткий контроль на цели;
- после снятия — короткий иммунитет;
- повторное гендзюцу от того же кастера слабее;
- боссы не должны контролироваться надолго;
- клиент не может сам снять гендзюцу без серверной проверки.

# 18. Сенсорика

## 18.1. Концепция
Сенсорика — это **отдельные техники**, а не один глобальный режим.

Каждая сенсорная техника:
- изучается отдельно;
- имеет уровень;
- тратит чакру;
- имеет радиус;
- имеет точность;
- может быть активирована через тот же слот.

---

## 18.2. Режимы для MVP

### `danger_sense`
- показывает направление угрозы;
- без точных координат;
- дёшево.

### `chakra_sense`
- показывает существ с чакрой;
- примерно;
- дороже.

---

## 18.3. Будущие режимы
- `entity_trace`
- `intent_reading`
- `byakugan_sense`
- `sharingan_tracking`

---

## 18.4. Серверный скан
```text
1. Если сенсорика активна:
   списывать чакру
2. Если чакра кончилась:
   выключить
3. Раз в scanIntervalTicks:
   найти цели в радиусе
   отфильтровать по типу режима
   отправить клиенту только разрешённые данные
```

---

## 18.5. Клиентский рендер
- стрелки угрозы;
- мягкие маркеры;
- контуры только если техника это разрешает;
- не показывать то, что сервер не разрешил.

## 19.2. Теги кланов
Добавить:
```text

```

---

## 19.3. Выбор клана
- При первом входе игрок выбирает клан сам.
- После выбора:
  - назначаются бонусы;
  - назначаются стартовые техники;
  - формируются `innateElements`.

---

## 19.4. Стартовые техники
Правило:
- `startingJutsu` изучаются сразу при вступлении в клан;
- если техника элементная и стихия ещё не открыта, техника изучена, но не может быть использована до открытия стихии.

Это честно и не ломает твою логику аттюнмента.

---

## 19.5. Смена клана
Правило:
```text
canChangeTo(targetClan):
  targetClan.tags.contains("nukekin") == true
```

### Что происходит при смене
- старые изученные техники не удаляются;
- старые клановые техники остаются изученными;
- новые клановые техники старого клана больше нельзя изучать;
- техники нового клана доступны по его правилам.

---

## 19.6. Проверка клановых требований

### Для каста
```text
если у техники есть clanRequired:
  разрешить, если текущий клан совпадает
  иначе разрешить, если техника уже была изучена до смены клана
```

### Для изучения
```text
если у техники есть clanRequired:
  изучение разрешено только если текущий клан совпадает
```

Это реализует принцип:
- старое не теряется;
- новое остаётся эксклюзивным.

# 26. Известные грабли, которые нельзя повторять

Это прямо из прошлых документов, и их нужно учитывать в реализации.

## 26.1. Нельзя
- использовать `Blocks.WOOL` вместо проверки `instanceof WoolBlock`;
- отменять `tickMovement`, если это ломает физику;
- делать агрессивные клиентские перехваты движения;
- держать статические мапы без очистки по `UUID`;
- смешивать клиентскую логику с серверными решениями;
- плодить классы по 500+ строк.

## 26.2. Нужно
- критическая логика только на сервере;
- клиентский код отдельно;
- любые изменения мира через безопасный менеджер;
- один патч → одна сборка;
- все игровые файлы в UTF-8 без BOM;
- если скрипт не нашёл паттерн — остановка с ошибкой.

## 1. Ошибки PowerShell-скриптов

### 1.1 Тернарный оператор в PS 5.1
| | |
|---|---|
| **Скрипт** | `audit_project.ps1` |
| **Ошибка** | `Непредвиденная лексема "?" в выражении или операторе` |
| **Код** | `$script:critCount += ($level -eq "CRIT" ? 1 : 0)` |
| **Причина** | Тернарный оператор `?:` доступен только в PowerShell 7+. В PS 5.1 он не поддерживается. |
| **Решение** | Заменено на `if/elseif/else` |
| **Как избежать** | Всегда проверять версию PowerShell. Для PS 5.1 использовать только классические конструкции `if/else`. |

```powershell
# ПЛОХО (PS 5.1)
$count += ($x -eq "A") ? 1 : 0

# ХОРОШО (PS 5.1)
if ($x -eq "A") { $count += 1 }
```

### 1.2 Кириллица и спецсимволы в строках
| | |
|---|---|
| **Скрипт** | `run_tests.ps1` |
| **Ошибка** | `Отсутствует закрывающий знак "}"` / `Непредвиденная лексема ")"` |
| **Код** | `Write-Host "  SHINOBICORE TEST SUMMARY — $timestamp"` |
| **Причина** | Символ `—` (em-dash, U+2014) ломает парсер при определённых кодировках файла. Аналогично с кириллицей в PS 5.1. |
| **Решение** | Заменено на ASCII-дефис `-` и английские строки |
| **Как избежать** | В PowerShell-скриптах использовать **только ASCII-символы**. Кириллицу — только в выводимых строках и только при 100% уверенности в кодировке файла UTF-8 без BOM. |

### 1.3 Экранирование кавычек в строках
| | |
|---|---|
| **Скрипт** | `apply_fixes.ps1`, `fix_tree_json.ps1` |
| **Ошибка** | `Отсутствует ")" в вызове метода` |
| **Код** | `$c = $c.Replace("},""requiresDojutsu""", ""requiresDojutsu""")` |
| **Причина** | Неправильное экранирование двойных кавычек внутри PowerShell-строк. `""` внутри `"..."` экранирует кавычку, но при вложенности легко запутаться. |
| **Решение** | Использование here-строк `@'...'@` для многострочных подстановок. |
| **Как избежать** | Для сложных подстановок использовать here-строки. Для простых Replace — одинарные кавычки. |

```powershell
# ПЛОХО
$c = $c.Replace("},""field""", ""value""")

# ХОРОШО
$c = $c.Replace('},"field"', '"field"')

# ЛУЧШЕ — here-строки для многострочных паттернов
$old = @'
старый код
'@
$new = @'
новый код
'@
$c = $c.Replace($old, $new)
```

### 1.4 BOM при создании файлов
| | |
|---|---|
| **Скрипт** | `create_code_dump.ps1` |
| **Ошибка** | Java-компилятор: `illegal character: '\ufeff'` |
| **Причина** | `[System.IO.File]::WriteAllText()` по умолчанию может добавить BOM, или файл создавался через PowerShell-командлеты, которые добавляют BOM. |
| **Решение** | Явное указание `New-Object System.Text.UTF8Encoding($false)` |
| **Как избежать** | Всегда использовать `UTF8Encoding($false)` при записи файлов из PowerShell. |

```powershell
# ПЛОХО — может добавить BOM
Set-Content -Path $file -Value $content -Encoding UTF8

# ХОРОШО — без BOM
$utf8 = New-Object System.Text.UTF8Encoding($false)
[System.IO.File]::WriteAllText($file, $content, $utf8)
```

### 1.5 Политика выполнения скриптов
| | |
|---|---|
| **Ошибка** | `Невозможно загрузить файл, так как выполнение сценариев отключено` |
| **Причина** | PowerShell по умолчанию блокирует выполнение `.ps1` файлов |
| **Решение** | Запуск с флагом `-ExecutionPolicy Bypass` |
| **Как избежать** | Всегда запускать: `powershell -ExecutionPolicy Bypass -File ".\script.ps1"` |

## 2. Ошибки компиляции Java

### 2.1 Несуществующие константы блоков (MC 1.20.1)
| | |
|---|---|
| **Файл** | `ElementInteractionManager.java` |
| **Ошибка** | `cannot find symbol: variable WOOL` |
| **Код** | `b == Blocks.WOOL` |
| **Причина** | В Minecraft 1.20.1 шерсть разделена по цветам (`WHITE_WOOL`, `BLACK_WOOL` и т.д.). Единого `Blocks.WOOL` не существует. |
| **Решение** | Заменено на `b instanceof WoolBlock` |
| **Как избежать** | Перед использованием констант `Blocks.*` проверять их существование в Yarn-маппингах 1.20.1. Для обобщённых проверок использовать `instanceof` с базовым классом блока. |

```java
// ПЛОХО — Blocks.WOOL не существует в 1.20.1
if (b == Blocks.WOOL) { ... }

// ХОРОШО
if (b instanceof net.minecraft.block.WoolBlock) { ... }
```

### 2.2 Отсутствие импортов
| | |
|---|---|
| **Файл** | `NinjaProjectileEntity.java` |
| **Ошибка** | `cannot find symbol: class ServerPlayerEntity` |
| **Причина** | Класс использован, но `import net.minecraft.server.network.ServerPlayerEntity` отсутствует. Скрипт-генератор не добавил импорт. |
| **Как избежать** | После генерации/патча файла проверять список импортов. В скриптах всегда проверять наличие нужных импортов и добавлять при отсутствии. |

### 2.3 Дубликаты методов при патчинге
| | |
|---|---|
| **Файл** | `NinjaPlayerData.java` |
| **Ошибка** | `method getActiveDojutsu() is already defined in class` |
| **Причина** | Скрипт патчинга запустился дважды (или паттерн не совпал при первом запуске, но метод уже был добавлен ранее). |
| **Как избежать** | В функции `Patch-File` всегда проверять `$c.Contains($new)` **до** замены. Если патч уже применён — пропускать. |

```powershell
# Защита от двойного применения
if ($c.Contains($new)) {
    Write-Host "[SKIP] Already applied" -ForegroundColor Yellow
    return
}
```

### 2.4 Файл в неверной директории
| | |
|---|---|
| **Файл** | `FormulaTest.java` |
| **Ошибка** | `cannot find symbol: package org.junit.jupiter.api` |
| **Причина** | Тестовый файл создан в `src/main/java` вместо `src/test/java`. В `main` нет зависимости JUnit. |
| **Как избежать** | Тестовые файлы всегда размещать в `src/test/java`. Зависимость `testImplementation` добавлять в `build.gradle`. |

### 2.5 Несовместимость API версий
| | |
|---|---|
| **Файлы** | Различные entity/mixin файлы |
| **Ошибка** | `cannot find symbol` для методов/полей |
| **Примеры** | `ProjectileUtil.getEntityHitResult` (другая сигнатура), `ModelPart.swing` (нет поля), `Direction.fromHorizontalDegrees` (нет метода), `ProjectileEntity.tick()` не перемещает сущность |
| **Причина** | Код писался под другую версию MC или Fabric API. |
| **Как избежать** | Перед написанием кода проверять Yarn-маппинги конкретной версии. Вести список «граблей» в `CONTEXT.md`. |

## 3. Ошибки данных (JSON)

### 3.1 Дубликаты узлов в `tree.json`
| | |
|---|---|
| **Ошибка** | Узлы `med_poison`, `gen_basic`, `water_dragon_n` объявлены дважды |
| **Причина** | При добавлении новых узлов в конец массива не проверилось, не существует ли узел с тем же `id` |
| **Как избежать** | Перед добавлением узла проверять уникальность `id`. В скриптах патчинга проверять `$tree.Contains('"id":"новый_id"')`. |

### 3.2 Сломанные ссылки `requires`
| | |
|---|---|
| **Ошибка** | 8 узлов ссылаются на несуществующие `requires` |
| **Причина** | При удалении/переименовании узлов не обновлены ссылки в зависимых узлах |
| **Как избежать** | После любых изменений `tree.json` запускать валидатор, проверяющий что все `requires` ссылаются на существующие `id`. |

### 3.3 Сиротские узлы
| | |
|---|---|
| **Ошибка** | Узлы `fire_expl`, `water_prison_n` ссылаются на удалённые техники |
| **Причина** | При удалении техник (дублей) не удалены соответствующие узлы дерева |
| **Как избежать** | При удалении техники искать все узлы с данным `jutsuId` и удалять/обновлять их. |

### 3.4 Циклическая зависимость
| | |
|---|---|
| **Ошибка** | Алгоритм обхода дерева ушёл в бесконечную рекурсию (depth 999) |
| **Причина** | Два узла ссылались друг на друга через `requires` |
| **Как избежать** | При добавлении `requires` проверять, не создаётся ли цикл. В валидаторе использовать DFS с отслеживанием посещённых узлов. |

### 3.5 Отсутствие полей в JSON техник
| | |
|---|---|
| **Ошибка** | При добавлении полей `requiresDojutsu`/`requiresScroll` в `JutsuDefinition`, не все JSON-файлы были обновлены |
| **Причина** | Поля добавлены в Java-код, но не все JSON-файлы техник получили новые поля |
| **Как избежать** | При добавлении опциональных полей в Java — делать их nullable и проверять на null. Для обязательных полей — скрипт миграции всех JSON. |

## 4. Архитектурные ошибки

### 4.1 Клиентский паркур без серверной валидации
| | |
|---|---|
| **Проблема** | Wall-run, Slide, Dodge работают полностью на клиенте |
| **Риск** | Читерство, рассинхронизация в мультиплеере |
| **Как избежать** | Всегда дублировать критическую логику на сервере. Клиент — визуал и отклик, сервер — валидация и авторитет. |

### 4.2 Статические Map без очистки
| | |
|---|---|
| **Проблема** | `SummonBehavior`, `MarkTracker`, `RasenshurikenServerManager` хранят статические Map |
| **Риск** | Утечка памяти при долгой работе сервера |
| **Как избежать** | Для каждого статического Map добавлять метод `clearPlayer(UUID)` и вызывать его при `ServerPlayConnectionEvents.DISCONNECT`. |

### 4.3 Отладочные `System.out.println` в продакшене
| | |
|---|---|
| **Проблема** | 16+ строк `System.out.println("### RASEN-DEBUG ###...")` |
| **Риск** | Засорение консоли, снижение производительности |
| **Как избежать** | Использовать `ShinobiCore.LOGGER.debug()` для отладки. Перед коммитом искать `System.out.print` и заменять. |

### 4.4 Чтение PacketByteBuf внутри server.execute()
| | |
|---|---|
| **Проблема** | `buf.readInt()` вызывается внутри `server.execute()` |
| **Риск** | К моменту выполнения лямбды буфер уже может быть перезаписан |
| **Как избежать** | Читать все данные из буфера **до** `server.execute()`, сохранять в final-переменные. |

```java
// ПЛОХО
ServerPlayNetworking.registerGlobalReceiver(ID, (server, player, handler, buf, sender) -> {
    server.execute(() -> {
        int value = buf.readInt(); // ОПАСНО!
    });
});

// ХОРОШО
ServerPlayNetworking.registerGlobalReceiver(ID, (server, player, handler, buf, sender) -> {
    final int value = buf.readInt(); // Читаем ДО server.execute()
    server.execute(() -> {
        // используем value
    });
});
```

## 7. Чеклист для будущих сессий

### Перед написанием PowerShell-скрипта:
- [ ] Только ASCII-символы в коде скрипта
- [ ] Нет тернарного оператора `?:`
- [ ] Here-строки `@'...'@` для многострочных подстановок

- [ ] Проверка `Contains($new)` перед патчем (защита от двойного применения)
- [ ] Запуск через `powershell -ExecutionPolicy Bypass -File`

### Перед написанием Java-кода:
- [ ] Проверить существование констант `Blocks.*` в Yarn 1.20.1
- [ ] Проверить сигнатуры методов в Fabric API 0.92.3
- [ ] Все импорты на месте
- [ ] Данные из PacketByteBuf читаются **до** `server.execute()`
- [ ] Для статических Map — метод очистки при disconnect
- [ ] Нет `System.out.println` — только `LOGGER`
- [ ] Тестовые файлы в `src/test/java`

### Перед изменением JSON:
- [ ] Проверить уникальность `id` перед добавлением
- [ ] После удаления техники — проверить все `jutsuId` в tree.json
- [ ] После изменения узлов — проверить все `requires`
- [ ] Запустить валидатор дерева на циклы

### Перед сборкой:
- [ ] `build.gradle`, `fabric.mod.json`, `mixins.json` — версии Java совпадают
- [ ] Все новые зависимости добавлены в `build.gradle`
- [ ] `.\gradlew.bat build` проходит без ошибок

# 📋 ОТЧЁТ: Ошибки при разработке ShinobiCore (07.08–15.08.2026)

## 1. Ошибки компиляции Java

| № | Ошибка | Причина | Как избежать |
|---|--------|---------|--------------|
| 1.1 | `variable hasKatana is already defined` (ClientInputHandler:55) | Вставляемый блок объявил `boolean hasKatana`, хотя переменная уже существовала выше в методе | Перед вставкой сниппета проверять, какие идентификаторы уже объявлены в целевом методе; вставкам давать уникальные имена или переиспользовать существующие переменные |
| 1.2 | `cannot find symbol: tryIaiDash(...)` | Клиентский код вызвал метод, который **никогда не был создан** в `KenjutsuClientHandler` | Правило «контракта»: сначала метод-реализация, потом вызов; оба изменения — в одном патче. После патча: `Select-String` должен находить и объявление, и вызов |
| 1.3 | `cannot find symbol: ModelPart.getRotation()` | Код сгенерирован «по общим знаниям» без проверки маппингов Yarn 1.20.1. В 1.20.1 у `ModelPart` есть `rotate(MatrixStack)`, но нет `getRotation()` | Держать список «граблей API» (см. раздел 6); каждое новое расхождение добавлять туда до генерации кода |
| 1.4 | `PlayerEntityModel<AbstractClientPlayerEntity> cannot be converted to FeatureRendererContext<...>` | В конструктор `FeatureRenderer` передали **модель**, а нужен **контекст (рендерер)**; плюс неверный generic (`PlayerEntity` вместо `AbstractClientPlayerEntity`) | Шаблон фичи игрока: `extends FeatureRenderer<AbstractClientPlayerEntity, PlayerEntityModel<AbstractClientPlayerEntity>>`, в конструктор передаётся `playerEntityRenderer` |
| 1.5 | Пропущен `import ServerPlayerEntity`; `Blocks.WOOL` не существует | Незнакомые с версией API-константы; неполные импорты в сгенерированном коде | Компиляция сразу после каждого патча; в «граблях»: `WoolBlock` вместо `Blocks.WOOL` |

**Системная причина всех пунктов:** патчи применялись «пачкой», сборка запускалась в конце.
**Главное правило:** *один патч → один `gradlew.bat build`*.

## 2. Runtime-краши (падения клиента)

| № | Краш | Цепочка первопричин | Как избежать |
|---|------|---------------------|--------------|
| 2.1 | `NullPointerException: KeyBindings.TOGGLE_SCABBARD is null` (и ранее `IAI_DASH is null`) | Патч добавил **объявление** поля, но патч **регистрации** не применился (`[FAIL] pattern not found`) → поле осталось `null` → краш на первом тике | 1) Объявление+регистрация KeyBinding — только атомарно (одним Write-File всего файла). 2) Скрипт патчей должен **останавливаться** при FAIL, а не продолжать. 3) Self-check в `register()`: assert все поля non-null |
| 2.2 | (потенциальный) чтение `PacketByteBuf` внутри `server.execute()` | Буфер читается в сетевом потоке; внутри `execute()` он уже пуст | Читать buf в `final`-переменные **до** `server.execute()` (уже закреплено в `PARKOUR_ACTION_ID`) |

Пополняется при каждой новой ошибке. Текущий список:

9. KeyBinding: объявление без регистрации = NPE на первом тике.

## 7. Итоговые процессные правила (топ-7)

1. **Один патч → одна сборка.** Никаких «пачек» без промежуточного `build`.
2. **Скрипт патчей = контракт:** идемпотентность, нормализация CRLF, FAIL → остановка, итоговая сводка с exit-кодом.
3. **Атомарные изменения:** KeyBinding (declare+register), метод+вызов, предмет+модель+текстура+рецепт — только вместе.
4. **Валидаторы данных:** tree.json (уникальность/циклы/сироты), рецепты (существование ID), assets (предмет↔файлы) — запускать после каждой правки JSON.
5. **UTF-8 без BOM** для всех игровых файлов; **ASCII или BOM** для `.ps1`.
6. **Реестр граблей** (раздел 6) — читать перед генерацией любого кода под 1.20.1.
7. **Еженедельный аудит** (`audit_project.ps1`): System.out, дубликаты, мёртвые файлы, согласованность версий.

### В чём заключалась ошибка

Ошибка **«Путь содержит недопустимые знаки»** (Illegal characters in path) при вызове `[System.IO.Path]::GetDirectoryName($p)` возникает потому, что в строку, хранящую путь к файлу (`$p`), попал **скрытый символ перевода строки** (или возврата каретки).

**Почему это происходит в PowerShell:**
Если вы формируете путь в двойных кавычках `""` и случайно переносите строку (или используете `` `n ``), PowerShell превращает это в реальный невидимый управляющий символ (0x0A / 0x0D). 
Операционная система Windows и .NET категорически запрещают использование символов управления (включая переносы строк, табуляцию и т.д.) в именах файлов и папок. Как только `GetDirectoryName` или `WriteAllText` встречает такой символ, они падают с `ArgumentException`.

**Как это выглядит в коде (ОШИБКА):**
```powershell
# ПЛОХО: Случайный перенос строки внутри двойных кавычек
$p = "$base\network\
AttributeSyncPacket.java" 

# ПЛОХО: Явное использование `n в пути
$p = "$base\network`nAttributeSyncPacket.java"
```

**Как это исправить (ПРАВИЛЬНО):**
Проверьте в вашем скрипте `sprint0_s01_attributes.ps1` блок `[3/5] AttributeSyncPacket.java`. Убедитесь, что путь записан **строго в одну строку** и без спецсимволов.
```powershell
# ХОРОШО: Одинарные кавычки (безопасно) или двойные в одну строку
$p = "$base\network\AttributeSyncPacket.java"

# ЛУЧШЕ: Использование Join-Path (полная защита от опечаток)
$p = Join-Path $base "network\AttributeSyncPacket.java"
```

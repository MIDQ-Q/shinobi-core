# 3. Что реально незавершено в текущем состоянии

## 3.1. Движение и паркур

В дампе видно много диагностического кода вокруг movement:

- `ClientMovementState.java`
- `ClientMovementService.java`
- диагностика `isChargingJump`
- фиксы `DoubleJumpClient`
- дампы wall walk
- отладка водной ходьбы
- старые конфликтные миксины
- упоминания проблем с `tickMovement`, camera roll, wall model/render.

Это означает, что движение находится в состоянии:

> **частично реализовано, но нестабильно и может содержать дублирующиеся обработчики.**

Основные риски:

- два обработчика одного и того же действия;
- старый wall-run конфликтует с новым;
- клиентская физика расходится с серверным зеркалированием;
- миксины отменяют ванильную логику слишком рано;
- чакра тратится дважды;
- состояние прыжка/заряженного прыжка дублируется;
- отладочные логи остались в коде.

---

## 3.2. Чакра

По плану чакра должна быть:

- на клиенте;
- синхронизироваться с сервером только при изменении;
- иметь усталость, истощение, резерв;
- восстанавливаться через медитацию;
- управляться через конфиг;
- не ломать старые HUD-элементы.

В текущем коде есть следы старой чакры:

- `ChakraHudRenderer.currentChakra`
- `ChakraHudRenderer.maxChakra`
- `ChakraHudRenderer.exhausted`
- `ClientNinjaState.chakraMode`
- `IChakraComponent`
- `NinjaComponents.getChakra`

Но для стабильной версии 3.0 нужен единый контроллер:

> **нужен новый `ChakraClientController` / `ChakraService`, который станет единственным источником клиентской логики чакры.**

Иначе старые и новые системы будут давать:

- двойной расход;

# Фаза 2. Чакра V3

## Цель

Сделать единую стабильную систему чакры.

---

## 2.1. Клиентский контроллер чакры

Создать или привести к единому виду:

```java
com.example.shinobicore.chakra.client.ChakraClientController
```

Ответственность:

- хранит текущее значение чакры;
- хранит максимум;
- хранит усталость;
- хранит истощение;
- хранит резерв;
- включает/выключает чакра-режим;
- тратит чакру;
- восстанавливает чакру;
- отправляет серверу только изменения.

Пример методов:

```java
tickClient()
setChakra(float value)
addChakra(float value)
consumeChakra(float amount)
canUseChakra(float amount)
isChakraModeActive()
toggleChakraMode()
startMeditation()
stopMeditation()
getFatigue()
addFatigue(float amount)
reduceFatigue(float amount)
isExhausted()
syncToServerIfDirty()
```

---

## 2.2. Серверное зеркало чакры

Создать:

```java
com.example.shinobicore.chakra.server.ServerChakraMirror
```

Ответственность:

- хранит серверную копию;
- принимает клиентские изменения;
- логирует подозрительные значения;
- не наказывает жёстко;
- может санитарно ограничивать мусор.

Принцип из плана:

> Сервер не наказывает, не откатывает жестко, только пишет логи и санитарно ограничивает мусор.

---

## 2.3. Пакеты

Нужны пакеты:

```text
C2S_CHAKRA_UPDATE
C2S_CHAKRA_MODE_TOGGLE
C2S_MEDITATION_START
C2S_MEDITATION_STOP
S2C_CHAKRA_SYNC
```

Правило:

- клиент считает чакру локально;
- сервер получает только реальные изменения;
- сервер может прислать принудительный синк при необходимости.

---

## 2.4. Совместимость со старым HUD

Это позволит старому HUD работать, пока новый интерфейс не готов.

# 9. Что не надо делать прямо сейчас

Не нужно одновременно:

Это правильно. Это один из главных источников крашей.

Для версии 3.0 лучше принять:

> Новые игроки получают дефолтные значения. Старые данные из v1/v2 не переносим.

Это упростит архитектуру и избавит от необходимости чинить битые сохранения.

---

## 9.4. Не делать сервер жёстким карающим античитом

По текущему решению:

> Сервер только логирует подозрительные события и санитарно ограничивает мусор.

Это хорошо для одиночной игры и локального мира.

## 1. Архитектура и модули

### 1.1. Клиент-серверное разделение

- **Сервер** — вся критическая логика: урон, стоимость, кулдауны, хитбоксы, валидация, опыт, сохранение данных.
- **Клиент** — визуализация, звуки, HUD, предикшн движений, паркурная физика, сенсорные силуэты.
- **Синхронизация** — через кастомные пакеты (см. `network/ModPackets.java`).

### 1.2. Основные модули

| Модуль | Описание |
|--------|----------|
| `stat` | Атрибуты игрока: чакра, стамина, уровни статов, стихий, резерв. |
| `clan` | Кланы (JSON), бонусы к статам, стоимости, усталости, додзюцу. |
| `jutsu` | Техники (JSON), поведение (BehaviorRegistry), каст, зарядка. |
| `tree` | Древо навыков (JSON), узлы, требования, пассивные бонусы. |
| `combat` | Боевые формулы: тай-дзюцу, кен-дзюцу, комбо, парирование. |
| `entity` | Кастомные сущности: снаряды, расенган, расенсюрикен. |
| `client` | Клиентские системы: HUD, камера, паркур, анимации, рендеры. |
| `network` | Пакеты синхронизации (сервер↔клиент). |
| `dojutsu` | Додзюцу (JSON): Шаринган, Бьякуган. |
| `item` | Предметы: катаны, броня, сюрикены, кунаи, свитки. |
| `mixin` | Миксины для модификации ванильного поведения. |

## 2. Системы и их состояние

### 2.1. Статы и прокачка
- **Статы**: `control`, `ninjutsu`, `taijutsu`, `genjutsu`, `medical`, `space_time`, `perception`.
- **Стихии**: `fire`, `water`, `wind`, `lightning`, `earth`.
- **Резерв** (`reserve`) — увеличивает максимум чакры.
- **Тело**: `hp`, `speed`, `jump` (качаются за SP).
- **SP** — очки навыков, тратятся на повышение уровней и открытие узлов древа.
- **Опыт** — начисляется за использование техник, медитацию, тренировки.
- **Формулы** — в `NinjaFormula.java`, все параметры вынесены в `ModConfig`.

### 2.2. Кланы
- Загружаются из `data/shinobicore/clans/*.json`.
- Дают:
  - `affinity` (родная стихия)
  - `statBonuses` (бонусы к статам)
  - `natureBonuses` (бонусы к стихиям)
  - `costMultiplier` (множители стоимости для стихий)
  - `fatigueMultiplier`
  - `reserveBonus`
  - `dojutsuHook` (автоматически даёт додзюцу)
- При входе игроку автоматически назначается случайный клан (если не выбран).
- Клан сохраняется в NBT игрока (`NinjaPlayerData`).

### 2.3. Техники (Jutsu)
- Описываются в `data/shinobicore/jutsu/*.json`.
- **Поля**: `id`, `name`, `category`, `nature`, `type`, `behaviorClass`, `params`, `baseCost`, `baseDamage`, `strain`, `requirements`, `requiresDojutsu`, `requiresScroll`.
- **Behavior** — реализует логику каста. Встроенные: `projectile`, `aoe`, `dash`, `melee`, `wall`, `utility`, `genjutsu`, `custom` (Java-класс).
- **Каст** — через `JutsuCaster.cast()` (сервер). Проверяет чакру, статы, требования, додзюцу/свитки, списывает ресурсы, вызывает Behavior.
- **Зарядка** — техники с флагом `chargeable` используют `beginCast()` и тикают через `CastingServerState`.

### 2.4. Древо навыков (Skill Tree)
- Загружается из `data/shinobicore/skill_tree/tree.json`.
- **Узлы** — имеют `id`, `branch`, `distance`, `angleOffset`, `type` (jutsu/passive), `jutsuId`, `effect`, `value`, `spCost`, `requires`, `clanRequired`, `visibilityCondition`.
- **Ветки** — описаны в `branches` (цвет, угол, название, клановая привязка).
- **Видимость** — узлы могут быть скрыты до выполнения условий (уровень стата, стихии, открытие другого узла, клан).
- **Разблокировка** — клиент отправляет пакет `UNLOCK_NODE_ID`, сервер проверяет требования и списывает SP.

### 2.5. Боевая система

#### Тай-дзюцу
- Стили: `STANDARD`, `STRONG_FIST` (разблокируется на уровне 50 тайдзюцу).
- Комбо из 4 шагов, время окна 1500 мс (+ бонусы от древа).
- Удар ногой (V) — x1.5 урона, отдельный кулдаун.
- Формулы урона/кулдауна в `TaijutsuFormulas`, анти-чит на сервере.

#### Кен-дзюцу (катаны)
- Стойки: `aggressive`, `seigan`, `iai`.
- Комбо из 6 шагов (шаг 5 — финишер 360°).
- Спец. атаки: прыжок (LMB в воздухе) — x2.5, спринт (LMB при спринте) — x1.6.
- `iai` стойка даёт рывок (Alt) с x3.0 урона.
- Парирование (X) — отражает снаряды, в стойке `seigan` — 360° защита и генерация чакры.
- Интеграция с чакрой: в чакра-режиме урон усиливается, каждый удар даёт +5% бонуса за комбо (макс +50%).

#### Оружие
- Катаны (железная, алмазная, незеритовая) — без прочности.
- Сюрикены, кунаи — метательные, с авто-прицеливанием (perception).
- Свитки — хранят ID техники, дают доступ к S-рангу.

### 2.6. Паркур
- Реализован в `client/parkour/` и `ChakraPhysicsClient`.
- Действия: слайд, бег по стенам, захват края, заряженный прыжок, кувырок, уворот, ползание.
- Требует чакра-режима, тратит чакру/стамину.
- Синхронизация позы через пакет `pose_sync`.

### 2.7. Чакра-режим
- Включается клавишей L, тратит чакру со временем.
- Даёт: хождение по воде, усиление прыжков/скорости, ауру (частицы), бонус к урону техник.
- Отключается при нуле чакры.

### 2.8. Расенган / Расенсюрикен
- **Расенган** — зарядка (зависит от `control`), готовность отображается в HUD, удар ЛКМ — рывок + урон по площади.
- **Расенсюрикен** — зарядка над головой, бросок ПКМ — летящий снаряд, взрыв + зона DoT.
- Сущности: `RasenganHandEntity`, `RasenshurikenEntity`.

### 2.9. Сенсорика и додзюцу
- **Сенсорика** — узлы древа дают пассивные способности: свечение врагов (`sen_glow`), опасность (`sen_danger`).
- **Додзюцу** — загружаются из JSON, привязаны к кланам. Шаринган даёт доступ к Аматерасу, Бьякуган — к техникам Хьюга.
- Активное додзюцу сохраняется в `NinjaPlayerData.activeDojutsu`.

### 2.10. HUD
- Кастомные полосы (чакра, усталость, еда, воздух, броня).
- Индикаторы: лоуаты A/B, комбо-счётчик, стиль, стойка, кулдаун удара ногой, зарядка расенгана.
- Отображается только на клиенте, данные синхронизируются пакетами.

### 2.11. Визуал и рендер
- Воксельные 3D-модели для катан, брони, ножен (через `BuiltinItemRenderer` и `FeatureRenderer`).
- Снаряды используют `NinjaProjectileRenderer` с цветными квадами.
- Расенган/Расенсюрикен — процедурные меши с вращением.
- Анимации: нарuto-бег, удары, парирование, каст (печати рук), лендинг.

### 2.12. Сеть (пакеты)
- **Сервер→Клиент**: `chakra_sync`, `loadout_sync`, `stats_sync`, `body_sync`, `catalog_sync`, `rasengan_sync`, `tree_sync`, `danger_sync`, `cast_fx`, `hit_stop`, `cast_start`, `cast_interrupt`.
- **Клиент→Сервер**: `meditate`, `select_slot`, `cast_slot`, `set_slot`, `spend_sp`, `chakra_mode`, `taijutsu_attack`, `taijutsu_kick`, `taijutsu_style`, `parkour_action`, `dodge`, `pose_sync`, `rasengan_strike`, `throw_rasenshuriken`, `sensory_toggle`, `unlock_node`, `attunement`, `control_train`, `iai_dash`.

## 3. Известные грабли и ошибки (важно для нейросети!)

> **ВСЕ ПЕРЕЧИСЛЕННЫЕ ОШИБКИ УЖЕ УЧТЕНЫ В КОДЕ, НО ПРИ ГЕНЕРАЦИИ НОВОГО КОДА ИХ НЕЛЬЗЯ ПОВТОРЯТЬ!**

### 3.1. Ошибки API Minecraft 1.20.1 / Yarn

| Что НЕЛЬЗЯ | Что ИСПОЛЬЗОВАТЬ |
|------------|------------------|
| `Blocks.WOOL` | `b instanceof WoolBlock` |
| `ModelPart.getRotation()` | `modelPart.rotate(matrices)` |
| `ModelPart.swing` | нет такого поля, использовать `pitch/yaw/roll` |
| `Direction.fromHorizontalDegrees` | `Direction.fromRotation()` |
| `ProjectileEntity.tick()` (не двигает) | вручную `setPosition(velocity)` |
| `ProjectileUtil.getEntityHitResult` | ручной `Box.raycast()` |
| `ParticleTypes.FALLING_DUST` (требует BlockState) | `ParticleTypes.POOF` для земли |
| `FeatureRenderer` конструктор с моделью | конструктор принимает **контекст рендерера** (FeatureRendererContext) |
| `PacketByteBuf` чтение внутри `server.execute()` | читать ДО `execute()`, сохранять в final переменные |
| Объявление KeyBinding без регистрации | сразу регистрировать `KeyBindingHelper.registerKeyBinding` |
| Использование `System.out.println` | использовать `ShinobiCore.LOGGER` |

### 3.2. Ошибки PowerShell (для скриптов патчинга)

| Что НЕЛЬЗЯ | Что ИСПОЛЬЗОВАТЬ |
|------------|------------------|
| Тернарный оператор `?:` (PS 5.1 не поддерживает) | `if/else` |
| Кириллица и спецсимволы в коде скрипта | только ASCII, кроме выводимых строк с гарантированной кодировкой |
| Неэкранированные кавычки в `Replace` | для сложных подстановок использовать here-строки `@'...'@` |
| `Set-Content -Encoding UTF8` (добавляет BOM) | `[System.IO.File]::WriteAllText($path, $content, (New-Object System.Text.UTF8Encoding $false))` |
| Перенос строки внутри пути | путь всегда одной строкой, использовать `Join-Path` |

### 3.3. Ошибки JSON / данных

- **Уникальность ID** — перед добавлением узла в `tree.json` проверять, что такого ID нет.
- **Ссылки** — при удалении/переименовании техники обновлять все `requires`, `jutsuId` в зависимых узлах и рецептах.
- **Циклы** — при добавлении `requires` убедиться, что не создаётся цикл (DFS).
- **Ресурсы** — новый предмет = минимум 3 файла (Java-класс, модель, текстура). Броня — ещё и armor-layer текстуры.
- **Lang-файлы** — обновлять вместе с изменением биндов клавиш.

### 3.4. Архитектурные ошибки

- **Клиент-сервер** — критическая логика только на сервере. Клиент — только визуал и быстрый отклик. Любой клиентский код на сервере должен быть обёрнут в `if (world.isClient)`.
- **Статические коллекции** — каждая статическая `Map` должна иметь метод очистки по `UUID` игрока и вызываться при `ServerPlayConnectionEvents.DISCONNECT`.
- **God-классы** — не создавать классы >300 строк. Разбивать на модули.

## 4. Правила разработки (для нейросети)

### 4.1. Общие принципы

1. **Один патч → одна сборка.** Никогда не применять серию изменений без промежуточной компиляции (`.\gradlew.bat build`). После каждого изменения сразу проверять компиляцию.
2. **Атомарность.** Связанные изменения делать только вместе: объявление + регистрация KeyBinding, метод + его вызов, предмет + модель + текстура + рецепт.
3. **Идемпотентность скриптов.** Любой скрипт патчинга должен проверять, не применён ли уже патч (`if ($c.Contains($new)) { skip }`), и нормализовать переводы строк (`$c.Replace("`r`n","`n")`).
4. **FAIL = STOP.** Если скрипт не находит паттерн для замены, он должен остановиться с ошибкой, а не продолжать работу.
5. **Кодировки:**
   - Все игровые файлы (Java, JSON, ресурсы) — **UTF-8 без BOM**.
   - PowerShell-скрипты — **ASCII** (или UTF-8 с BOM, если необходим русский текст, но лучше избегать).
   - Запись файлов из PowerShell — только `[System.IO.File]::WriteAllText($path, $content, (New-Object System.Text.UTF8Encoding $false))`.
6. **Пути в скриптах** — всегда одной строкой, без `\n` или реальных переносов. Использовать `Join-Path`.
7. **Логирование** — только через `ShinobiCore.LOGGER` (никаких `System.out.println`).
8. **Валидация данных.** После изменения `tree.json`, рецептов, моделей — запускать соответствующие валидаторы (или писать их сразу). Проверять уникальность ID, корректность ссылок `requires`, отсутствие циклов, существование всех предметов и текстур.

### 4.2. Синтаксис и структура Java

- Перед вставкой кода проверять, не объявлена ли уже переменная с таким именем в методе. Если да — переиспользовать её или дать уникальное имя.
- Не вызывать метод, который ещё не создан. Сначала реализация, потом вызов, оба изменения в одном патче.
- Импорты должны быть полными. После генерации кода проверять, что все используемые классы импортированы.
- Избегать вложенных тернарников (читаемость/риск ошибок) — использовать `if/else`.
- Не дублировать одинаковые блоки кода — выносить в отдельные методы.
- Тестовые файлы размещать только в `src/test/java`.
- Следить за согласованием версий: `build.gradle`, `gradle.properties`, `fabric.mod.json`, `*.mixins.json` должны указывать одну версию Java (сейчас Java 17).

## 8. Пример хорошего мастер-скрипта

```powershell
# Применяет патч к файлу, проверяя, что он ещё не применён
function Patch-File($p, $old, $new) {
    if (-not (Test-Path $p)) { Write-Host "[MISS] $p" -ForegroundColor Red; return }
    $c = [System.IO.File]::ReadAllText($p, $utf8)
    if ($c.Contains($new)) { Write-Host "[SKIP] already applied" -ForegroundColor Yellow; return }
    if (-not $c.Contains($old)) { Write-Host "[FAIL] pattern not found" -ForegroundColor Red; return }
    $c = $c.Replace($old, $new)
    [System.IO.File]::WriteAllText($p, $c, (New-Object System.Text.UTF8Encoding $false))
    Write-Host "[OK] patched $p" -ForegroundColor Green
}
```

### 10.2. С какими проблемами столкнулись и как их решили (Учтенные грабли)
*ВНИМАНИЕ ДЛЯ ИИ: Эти проблемы были решены. При генерации нового кода НЕЛЬЗЯ их повторять.*

1. **Сеть и `PacketByteBuf`:**
   - *Проблема:* Чтение данных из `PacketByteBuf` внутри `server.execute()` или `client.execute()` вызывало краши, так как буфер уже освобождался сетевым потоком.
   - *Решение:* Всегда читать **ВСЕ** данные из буфера в `final` локальные переменные **ДО** вызова `execute()`.
2. **PowerShell и Патчинг (Скрипты):**
   - *Проблема:* Скрипты падали из-за различий в переносах строк (CRLF vs LF), BOM в UTF-8 и отсутствия тернарного оператора `?:` в PS 5.1.
   - *Решение:* Использовать `$c.Replace("`r`n", "`n")` для нормализации. Записывать файлы через `[System.IO.File]::WriteAllText` с `UTF8Encoding($false)`. Избегать тернарников, использовать `if/else`.
3. **Рендеринг и Миксины (Yarn 1.20.1):**
   - *Проблема:* `FeatureRenderer` требовал `FeatureRendererContext`, а не модель напрямую. `ModelPart` не имел метода `getRotation()`.
   - *Решение:* Передавать контекст рендерера. Использовать `modelPart.rotate(matrices)`. Для поворотов конечностей использовать `pitch/yaw/roll`.
4. **Физика и Рейкасты:**
   - *Проблема:* Ванильный `ProjectileUtil.getEntityHitResult` некорректно работал с кастомными хитбоксами и скоростями. `Direction.fromHorizontalDegrees` отсутствовал в маппингах.
   - *Решение:* Написан ручной `Box.raycast()` и векторная математика (cross-product для перпендикуляров при спавне стен и беге по стенам). Использовать `Direction.fromRotation()`.
5. **Утечки памяти (Статические коллекции):**
   - *Проблема:* Статические `Map<UUID, ...>` на клиенте и сервере текли при выходе игрока.
   - *Решение:* Добавлены методы `cleanup(UUID)` и вызовы очисток по событию `ServerPlayConnectionEvents.DISCONNECT`.
6. **Клиент-серверная авторитарность:**
   - *Проблема:* Клиент мог спамить пакеты атак, обходя кулдауны (читерство).
   - *Решение:* Внедрен серверный анти-чит в `ModPackets` (проверка `serverComboStep`, `lastAttackTimeMs` и валидация стиля).

### 11.3. Шаринган — принятые решения по способностям

Решения утверждены пользователем. Способности едины для SP и MP.

**Эволюция (комбинированная):**
- Использование: каст огненных/гендзюцу техник (+2), парирование (+1), получение урона (+1)
- Стресс: HP < 15%, почти летальный урон, бой с сильным врагом, каст при чакре < 10%
- Пороги: 1T = 50 usage + 1 stress, 2T = 150 + 2, 3T = 300 + 3, Мангекё = 500 + 5 + квест

**1 томое — Улучшенный трекинг:**
- MP: призрачный след (позиция 2 тика назад) + вектор движения
- SP: пути мобов + радиус агро + ранний телеграф атак
- Решение: вариант D (след + вектор), единый для SP/MP

**2 томое — Копирование техник:**
- 1 наблюдение для техник ниже A-ранга (T1-T3)
- Требуется открытая стихия цели
- Копия на 5 минут, стоимость x1.5 от оригинала
- Для SP: анализ — после 3 ударов моба одного типа, -15% урона от этого типа

**3 томое — Предвидение:**
- Отображение техники врага над головой (цвет стихии + название)
- 35% автопарирование ближних атак (кулдаун 2 сек)

**Мангекё:**
- Аматерасу: уже реализован как техника
- Перенос в измерение: телепорт + дебаффы (слепота, замедление, слабость, тошнота)
- Квестовая линейка: задел (`hasMangekyoQuest` boolean), реализация в будущем

## 3.2. Клиентская инициализация

Файл:

```text
src/main/java/com/example/shinobicore/ShinobiCoreClient.java
```

Рекомендуемый порядок:

1. Проверка, что мы на клиенте.

2. Регистрация клиентских приемников пакетов:

```java

```

3. Регистрация кейбиндов, если они нужны в этом спринте:

```java

```

4. Регистрация HUD-элементов в минимальном/отладочном виде.

5. Регистрация клиентских событий:

```java

```

6. Регистрация рендер-слоев только если они уже стабильны.

### Важно

Клиентская инициализация не должна:

- обращаться к серверным компонентам напрямую;
- рассчитывать урон;
- менять баланс;
- принимать геймплейные решения.

Клиент отвечает за:

- ввод;
- визуал;
- локальную физику там, где это разрешено;
- отправку запросов серверу.

Сервер отвечает за:

- проверку чакры;
- проверку кулдаунов;
- трату ресурсов;
- урон;
- прогресс;
- валидацию пакетов.

## 5.2. Критическое правило чтения пакетов

Из прошлых граблей:

> Читать `PacketByteBuf` нужно до `server.execute(...)`.

Правильная структура серверного обработчика:

```java
ServerPlayNetworking.registerGlobalReceiver(ModPackets.PROGRESSION_ACTION,
    (server, player, handler, buf, sender) -> {
        final int action = buf.readInt();
        final String payload = buf.readString();

        server.execute(() -> {
            // Здесь уже работаем с сервером
        });
    });
```

Неправильно:

```java
server.execute(() -> {
    int action = buf.readInt(); // ОШИБКА: буфер может быть уже освобожден
});
```

Минимальный набор:

### Клиент → сервер

1. `CHAKRA_MODE_TOGGLE`
   - запрос включения/выключения режима чакры.

2. `PROGRESSION_ACTION`
   - повышение стата;
   - покупка пассивки;
   - распределение очков.

1. `COMPONENT_SYNC`

2. `VFX_SPAWN`
   - визуальные эффекты.

3. `CLIENT_STATE_UPDATE`
   - обновление клиентского состояния для HUD.

## 5.4. Временная политика

Если какая-то фича еще не готова:

- пакет может быть зарегистрирован;
- обработчик может писать лог или возвращать безопасный отказ;
- но нельзя оставлять незарегистрированные идентификаторы, если клиент их отправляет.

### Результат

- все пакеты объявлены в одном месте;
- нет чтения буфера после `execute`;
- клиент и сервер используют одинаковые идентификаторы.

### Критерий готовности

- команда `/shinobicore packets` или `/testall` показывает список зарегистрированных пакетов;
- нет ошибок `Packet not registered`;
- тестовый пакет проходит клиент → сервер → ответ.

## Этап 7. Загрузка и валидация JSON-данных

Это очень важный этап, потому что в проекте уже есть данные для техник, кланов и дерева прокачки.

## 7.1. Что нужно загрузить

Минимальный набор:

```text
data/shinobicore/jutsu/*.json
data/shinobicore/clans/*.json
data/shinobicore/skill_tree/tree.json
```

---

## 7.2. Требования к загрузке

Загрузка должна быть:

- атомарной;
- безопасной;
- идемпотентной;
- с валидацией;
- с логированием ошибок;
- без падения сервера из-за одного битого файла.

---

## 7.3. Что проверять в файлах техник

Для каждого `jutsu`:

Обязательные поля:

- `id`;
- `name`;
- `element`;
- `behavior`;
- `cost`;
- `cooldown`.

Дополнительные:

- `params`;
- `mastery`;
- `projectile`;
- `damage`;
- `range`;
- `castTime`.

Ошибки:

- дублирующийся `id`;
- неизвестный `behavior`;
- отрицательный `cost`;
- отрицательный `cooldown`;
- пустой `name`.

---

## 7.4. Что проверять в кланах

Для каждого клана:

- `id`;
- `name`;
- `bonuses`;
- `affinities`;
- `passives`;
- `startingJutsu`.

Проверять:

- нет ли несуществующих техник в `startingJutsu`;
- нет ли несуществующих пассивок;
- нет ли дублей кланов.

---

## 7.5. Что проверять в дереве прокачки

Для каждого узла:

- `id`;
- `branch`;
- `type`;
- `distance`;
- `spCost`;
- `requires`;
- `jutsuId`, если `type == "jutsu"`.

Проверять:

- нет дублей узлов;
- все `requires` существуют;
- нет циклических зависимостей;
- `spCost >= 0`;
- если узел выдает технику, техника существует.

## 7.6. Файлы загрузчиков

Создать или обновить:

```text

src/main/java/com/example/shinobicore/data/SkillTreeDataLoader.java
src/main/java/com/example/shinobicore/data/DataValidationReport.java
```

### Результат

### Критерий готовности

## Этап 8. Разделение старого и нового кода

Это один из самых важных пунктов.

## 8.1. Проблема

В дампе есть старые куски:

- тай-дзюцу;
- паркур;
- HUD;
- Rasengan;
- sensory;
- wall walk;

Если все это активно одновременно с новым каркасом, возможны:

- дубли обработчиков;
- краши из-за старых миксинов;
- непредсказуемое поведение.

---

## 8.2. Что сделать

Разделить код на категории:

### Категория A: активно в версии 3

- ядро;
- логгер;
- конфиг;
- компоненты;
- сеть;
- команды;
- загрузка данных.

### Категория B: будет включено позже

- аттюнмент;
- древо прокачки;
- гендзюцу;
- техники;
- паркур;
- боевые системы.

### Категория C: временно отключить

- старые экспериментальные миксины;
- старые визуальные костыли;
- сломанный wall walk v2;
- дублирующие команды;
- незадействованные клиентские экраны;
- старые скрипты миграции.

---

## 8.3. Как отключать безопасно

Не обязательно сразу удалять файлы.

Можно:

1. Не регистрировать их в `ShinobiCore`.
2. Не регистрировать их в `ShinobiCoreClient`.
3. Не указывать их в `fabric.mod.json`.
4. Не включать их миксины в `shinobicore.mixins.json`.
5. Обернуть инициализацию в флаг:

```java
if (FeatureFlags.isLegacyTaijutsuEnabled()) {
    // временно выключено
}
```

## 8.4. Особое внимание к стенем

Из прошлых разборов:

- версия 2 хождения по стенам была проблемной;
- серверные `setVelocity` и лишние миксины ломали физику;
- стабильнее была клиентская физика из версии 1, где сервер только проверяет чакру и расход.

Рекомендация:

> В Sprint 1 не включать стену как активную систему.  
> Если включать позже — использовать клиентскую физику и серверную валидацию ресурсов, без серверного принудительного изменения скорости.

### Результат

Старый код больше не мешает новой архитектуре.

### Критерий готовности

- нет регистрации старых систем, которые не должны работать в Sprint 1;
- нет дублей команд;
- нет дублей пакетов;
- в `mixins.json` только актуальные миксины.

# 8. Что не нужно делать на этом шаге

Чтобы не сломать фундамент, не рекомендуется сейчас делать следующее.

## 8.1. Не делать полноценный аттюнмент

Аттюнмент — это уже контент поверх фундамента.

Сначала нужно:

- компонент прогресса;
- SP;
- control;
- открытие стихий;
- пакет `attunement_request`;
- серверная валидация.

Без этого аттюнмент снова станет костылем.

---

## 8.2. Не делать полноценное древо прокачки

Древо прокачки можно начать только после:

- загрузки `tree.json`;
- валидации узлов;
- компонента `SKILL_TREE`;
- пакета разблокировки;
- серверной проверки требований.

---

## 8.3. Не делать гендзюцу

Гендзюцу требует:

- статус-эффектов;
- резистов;
- серверной проверки цели;
- клиентского визуала;
- синхронизации.

Это уже следующий крупный блок.

---

## 8.4. Не включать сразу все старые боевые системы

Не нужно одновременно активировать:

- тай-дзюцу;
- кен-дзюцу;
- сюрикен-дзюцу;
- комбо;
- Rasengan;
- wall walk;
- sensory;
- HUD-иконки.

Сначала фундамент, потом по одному модулю.

---

## 8.5. Не делать жесткую зависимость от Iron's Spells

Если нет стабильной интеграции, не надо писать:

```json
"depends": {
    "irons_spells": "*"
}
```

Лучше:

- опциональная интеграция;

# 11. Риски и как их избежать

## Риск 1: старый код сломает новую архитектуру

Решение:

- не регистрировать старые системы сразу;
- использовать флаги;
- подключать по одному модулю.

---

## Риск 2: мод упадет из-за опциональной зависимости

Решение:

- не делать `depends` на Better Combat / GeckoLib / Iron's Spells;
- использовать `recommends`;
- проверять наличие через `FabricLoader`.

---

## Риск 3: ошибка в чтении пакетов

Решение:

- читать `buf` до `server.execute`;
- все данные сохранять в `final` переменные;
- внутри `execute` только использовать готовые значения.

---

## Риск 4: битый JSON сломает запуск

Решение:

- оборачивать чтение в `try/catch`;
- сохранять отчет;
- не падать;
- логировать путь к файлу и причину.

---

## Риск 5: клиентские классы попадут на сервер

Решение:

- клиентские классы только в `ShinobiCoreClient`;
- клиентские пакеты только в клиентской инициализации;
- не использовать клиентские классы в общих серверных методах.

---

## Риск 6: миксины из прошлых версий вызовут краш

Решение:

- проверить `shinobicore.mixins.json`;
- оставить только нужные;
- удалить или закомментировать старые;
- каждый миксин включать только после понимания, зачем он нужен.

---

# 15. Самый первый атомарный шаг

Если нужно выбрать один ближайший шаг, я бы начал с этого:

> **Сделать скрипт `sprint1_01_bootstrap.ps1`, который безопасно обновляет `build.gradle`, `gradle.properties`, `fabric.mod.json`, создает/проверяет `FeatureFlags`, `ModPackets`, базовые команды и запускает сборку.**

Этот шаг должен быть:

- идемпотентным;
- атомарным;
- с проверкой до и после;
- с промежуточной сборкой;
- без удаления большого количества старого кода на первом этапе.

Примерный состав скрипта:

1. Проверить наличие обязательных файлов.
2. Проверить, что патч еще не применен.
3. Обновить `gradle.properties`.
4. Обновить `build.gradle`.
5. Обновить `fabric.mod.json`.
6. Создать `FeatureFlags.java`, если его нет.
7. Создать `ModPackets.java`, если его нет.
8. Создать базовый `ShinobiCommands.java`, если его нет.
9. Запустить:

```powershell
.\gradlew.bat build
```

10. Вывести результат:
   - успешно;
   - ошибки сборки;
   - что делать дальше.

# 16. Финальная рекомендация

Сейчас не нужно пытаться “починить все старые системы сразу”.

Лучшая стратегия:

1. Зафиксировать версию 3.0 как стабильный скелет.
2. Сделать безопасный фундамент.
3. Подключить только то, что нужно для диагностики.
4. Старые системы временно заглушить.
5. После этого по одному включать модули:
   - аттюнмент;
   - древо прокачки;
   - гендзюцу;
   - боевые системы;
   - паркур;
   - визуал.

Это позволит избежать повторения прошлых проблем, когда несколько систем менялись одновременно и ломали друг друга.
